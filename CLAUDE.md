# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CrateDigger is a native **macOS** music-library utility (AppKit + SwiftUI, Swift Package Manager). It scans folders of audio files, browses/plays them, inspects & edits metadata and artwork, organizes/cleans up libraries, and batch-converts files with **FFmpeg**. It also has integrations for Subsonic/Navidrome streaming, Audio-CD ripping, YouTube "radio" streaming (via **yt-dlp**), splitting continuous vinyl-side rips into per-track exports, and Last.fm scrobbling. The UI is a skeuomorphic "hardware" aesthetic ("Carbon").

## Commands

```bash
swift build                      # build (debug). App binary: .build/debug/CrateDiggerApp
swift build -c release           # release build
scripts/test.sh                  # run the XCTest suite (preferred — see note below)
scripts/test.sh --filter OutputPathPlannerTests           # run one test class
scripts/test.sh --filter OutputPathPlannerTests/testFoo   # run one test method
scripts/package-app.sh           # assemble dist/CrateDigger.app (bundles ffmpeg/ffprobe/fpcalc, ad-hoc signed)
```

- **The debug binary lives at `.build/debug/CrateDiggerApp`.** `swift build` on this machine uses the Swift Build backend, which writes to `.build/out/Products/Debug/`; `.build/debug` is a symlink to that folder. The classic SwiftPM layout, `.build/arm64-apple-macosx/debug/CrateDiggerApp`, **does not exist here at all**: that path is gone, not just moved, so don't reintroduce it. (`.build/release` still resolves the old way, to `.build/arm64-apple-macosx/release`.)
- **Run `scripts/test.sh`, not bare `swift test`.** It forces `--enable-xctest --disable-swift-testing`, points at a full Xcode install, and uses a repo-local module cache (`.build/tests`). XCTest needs a *full* Xcode developer dir (not just Command Line Tools); the script prints clear remediation if the license isn't accepted or `PlatformPath` lookup fails.
- Tests live in `Tests/CrateDiggerCoreTests` (229 files, 2,538 tests, 11 of them skipped when their environment is missing; most of the coverage, since the core library is the testable layer) and `Tests/CrateDiggerAppTests` (39 files, 275 tests: theming, screen presets, `WindowFramePlanner`, `UpdateFeed`, yt-dlp retry, device-selection settings, the artist page's focus wiring). These counts drift; `scripts/test.sh` prints the real one. `FATSandboxTests` skip unless `CRATEDIGGER_FAT_SANDBOX` is set (see PodBox below).
- **SwiftUI views and `LibraryViewModel` are still untested**, and that is where bugs concentrate: the 2.0 Phase 0 whole-branch review found all three of its cross-task defects in view-model glue, not in Core. Anything that is a *decidable value* — which track was playing, which files belong to a folder, whether leaving a track counts as a skip — belongs in Core with a test, even when the surrounding wiring stays untested.
- To launch and verify a change in the running app, build then run the binary directly (the local permission allowlist already covers `swift build`, running the debug binary, and `pkill -f CrateDiggerApp`).
- Release/distribution (Developer ID signing + notarization + DMG) and the full beta gate are documented in `README.md` and `docs/BETA_RELEASE_CHECKLIST.md`.

## Two release lines (read before committing anything)

**2.2.4 shipped from `main` on 2026-10-03** (build 105). `main` is the stable
line, now 2.2.x: it is what the public downloads and what every installed copy
auto-updates from. Fixes for 2.2.x land on `main`.

**The 2.3 beta line is open on `v2.3`**, cut from `main` on 2026-10-03; 2.3.0
beta 1 is build 106 and brings the compact player. 2.3.0 reached RC 1 (build
109) but never shipped GA: on 2026-10-12 the line moved to **2.3.1** (2.3.1
beta 1, build 110, tag `v2.3.1-beta.110`), so the marketing version on `v2.3`
is now 2.3.1 and its CHANGELOG section is `## 2.3.1`. Release candidates on a
beta line set `channel = "RC"` and are tagged `v<version>-rc.<build>`. `v2.2` carried the 2.2 cycle
and then the 2.2.x betas and RCs (2.2.4 RC 104 was merged into `main` for GA);
like `v2` and `v2.1` it is kept for history only. **Do not branch new work from
`v2`, `v2.1` or `v2.2`.** A beta branch works like this: `AppVersion.channel` is `"BETA"`
there, betas are tagged `v<version>-beta.<build>` and published as GitHub
prereleases, their only audience is stable users who turned on Receive beta
updates, `main` is merged in before each beta so the beta never lacks a stable
fix, and at GA the branch is merged into `main` with `channel` set back to
`""`.

The mechanism that keeps the two lines apart:

- `SUFeedURL` in `Info.plist` points at the stable `website/appcast.xml` and
  is only the fallback for a build that overrides nothing. The real choice is
  made at runtime by `UpdateFeed.override(channel:betaOptIn:)` in
  `Updates/SoftwareUpdater.swift`:

  ```swift
  (!channel.isEmpty || betaOptIn) ? beta : nil
  ```

  A build whose `AppVersion.channel` is non-empty follows `appcast-beta.xml`
  automatically; a stable build reads the beta feed only if its owner turned
  on Advanced ▸ Receive beta updates. On `main`, `channel` is `""`; a beta
  branch sets `"BETA"`.
- Keeping that decision in one pure function rather than in `Info.plist` is
  the point: there is no per-branch line to repoint, and so none to forget.
  `UpdateFeedTests` covers all four channel/opt-in combinations and fails if
  `SUFeedURL` ever stops matching `UpdateFeed.stable`. **Do not "simplify"
  `UpdateFeed.override` into the plist.**
- `scripts/update-appcast.sh` generates each feed only on the branch that
  owns it (`appcast.xml` on `main`, `appcast-beta.xml` on `BETA_BRANCH`, `v2.3` for
  the 2.3 cycle) and refuses a DMG whose major version differs from what is
  already staged in `dist/updates*/`. When 2.1 started, the 2.0.0 beta DMG was
  moved to `dist/updates-beta/old_updates`; when 2.2 started, the 2.1.0 DMG
  followed it. When 2.3 started, the 2.2.x DMGs did. Existing feed entries keep the download URL they were published
  with, looked up by build in the committed feed: deriving it from the new tag
  would have pointed the 2.1.0 GA entry at a `v2.1.0-beta.89` that never existed.
- A stable build with Receive beta updates on reads **only** the beta feed, so
  every GA also gets an entry there, or opted-in users are never offered it.
  For 2.1.0 that entry was written on `v2.1` (fast-forwarded to `main` first)
  and only `website/appcast-beta.xml` was carried back to `main`. 2.1.1 got no
  beta-feed entry, so opted-in users sat on 2.1.0 until 2.2.0 beta 1.

When the next beta cycle starts (2.2, 3.0): cut its branch from `main`, set
`channel` there, change `BETA_BRANCH` in `update-appcast.sh` and the beta column
of the `press-the-record` skill, move the previous line's DMG out of
`dist/updates-beta/`, publish betas as GitHub prereleases so `/releases/latest`
stays on stable, and copy only `website/appcast-beta.xml` across to `main` when
publishing a beta feed. The 2.0.0 promotion was done by hand and is written up

## Two-target architecture

`Package.swift` defines two targets — keep the boundary clean:

- **`CrateDiggerCore`** (`Sources/CrateDiggerCore`) — a pure library: `Models/` + `Services/`. No AppKit *views*, no app state. This is the unit-tested layer; put logic here when it can be tested in isolation. Most types are `public`, `Sendable`, `Codable`.
- **`CrateDiggerApp`** (`Sources/CrateDiggerApp`) — the AppKit executable + all SwiftUI views, depends on Core.

Plus a small third target, **`NowPlayingFeed`** (`Sources/NowPlayingFeed`): the Codable record and file store the app writes into the app-group container for the **Now Playing widget**. The widget itself (`Sources/CrateDiggerWidget`) is **not** a SwiftPM target: WidgetKit only lists extensions built as Xcode's app-extension product type (a hand-wrapped SwiftPM binary registers and launches but never reaches the gallery), so `Packaging/CrateDiggerWidget/CrateDiggerWidget.xcodeproj` builds it, compiling the NowPlayingFeed sources directly, and `package-app.sh` embeds it in Developer ID builds only. The app writes the feed from `LibraryViewModel+NowPlaying` and only when the `.appex` is in its bundle, so a `swift build` run never touches the container. What the widget shows around the track (idle: library slideshow, last cover or a phrase; playing: cover, or cover and booklet) is picked in Settings ▸ Interface and travels inside the feed; the app renders the pictures it names into the container's `pictures/` folder through Core's `WidgetSlide`, off the main thread except for the playing cover. Families: small, medium and large. **An update strands the old extension**: the process the previous build launched keeps running, and chronod rejects everything it renders (`bundleStubNotSupported`, "Bundle version did not match"), so every reload fails and the widget freezes on its last frame. In 2026-09 this froze a slideshow for five days after a Sparkle update. `endStaleWidgetExtensionIfUpdated()` in `startWidgetFeed` handles it: once per new `AppVersion.build` it `pkill`s this bundle's extension executable and asks for a reload. Ending the extension alone was verified to be enough; chronod does not need restarting. When testing by hand with `swift build`, which carries no widget, kill the installed `CrateDiggerWidget` process yourself. Design: `docs/superpowers/specs/2026-09-11-now-playing-widget-design.md`.

### App launch & control flow

There is no `@main` / SwiftUI App lifecycle. The chain is explicit:

```
main.swift  →  AppDelegate  →  MainWindowController  →  CarbonHostingController  →  CarbonRootView (SwiftUI)
(NSApplication)  (menu bar,      (NSWindow: frame        (NSHostingController        (root view tree)
                  Space monitor)   persistence,            owns the single
                                   appearance)              LibraryViewModel)
```

- **`AppDelegate`** builds the entire NSMenu programmatically and is the target for every menu action. Menu actions forward to `MainWindowController`, which forwards to `LibraryViewModel`. `validateMenuItem` gates enablement on view-model state. It also installs a global Space-key monitor (AppKit swallows plain Space otherwise) for play/pause.
- **AppKit ↔ SwiftUI bridge:** the menu bar, window chrome, and all **sheets** are AppKit. Sheets are `NSViewController`s (e.g. `ConversionOptionsSheetController`, `AlbumFolderReviewSheetController`) presented via `presentAsSheet`, communicating results back through an `onDecision` closure. The main content is SwiftUI hosted in the window.

### `LibraryViewModel` — the center of gravity

`Sources/CrateDiggerApp/UI/Carbon/Library/LibraryViewModel.swift` (~5,850 lines) is a single `@MainActor ObservableObject` that owns **all** app state, **all** services, and **most** behavior. Almost every SwiftUI view binds to it via `@EnvironmentObject`. **When fixing app behavior, start here** — this is where the wiring lives.

Behavior is split across **37 `LibraryViewModel+*.swift` extensions in three
folders** (don't assume they are all beside the main file):

- `UI/Carbon/Library/` — `+ArrowNav`, `+ArtistPageFixture` (DEBUG), `+ArtistProfiles`, `+BatchArtwork`,
  `+BusySignals`, `+CDDetect`, `+CompactPlayer`, `+DeepScan`,
  `+LibraryFiles`, `+LibraryLocation`, `+Listening`, `+MetadataRepair`,
  `+MiniPlayer`, `+MissingFiles`, `+MultiSelect`, `+NowPlaying`, `+Onboarding`,
  `+Queue`, `+QuickEQ`, `+Radio`, `+RecordDivider`, `+Rename`, `+Resume`, `+SACDImport`,
  `+Search`, `+Sleep`, `+Stats`, `+StreamDownload`, `+TrackActions`,
  `+Versions`, `+Widget`
- `UI/Conversion/` — `+Conversion`
- `UI/ExternalDevices/` — `+ArtistPictures`, `+DeviceReview`, `+DeviceSync`, `+ExternalDeviceTransfer`, `+PodBox`

`find Sources -name "LibraryViewModel+*.swift"` is the reliable way to see them all.

It is a large god-object; prefer extracting testable logic into a Core service over adding more to it.

**Browser state is no longer here.** The view (`BrowserView`), the selection (one anchor per column plus at most one multi-selection set, in `BrowserSelection`), the four sort pairs, `focusedColumn` and the search `filter` live in Core's `BrowserState`; the view model holds one `@Published var browser` and forwards every old property name (`selectedArtistID`, `selectedAlbumIDs`, `selectArtist(...)`) onto whichever column shows that facet. Add browser state to `BrowserState`, not here. The sort and filter setters recompute themselves; `browser`'s own `didSet` only reacts to the view or the selection changing, and then recomputes just the columns to the right of the change.

### Browser views (any category in any column)

The browser is not hard-wired to Artist → Album → Track. A **`BrowserView`** is one to three **`BrowserFacet`**s (artist, album artist, album, genre, year, decade, format, rating, track), left to right; the only rules are no duplicates and Track last. **`BrowserCascade`** computes each column as its facet's values among the tracks surviving the columns to its left, resolving Artist and Album columns to the index's own objects so rows keep art and version groups. The index itself is a lookup, never the shape of the browser. Every source remembers its own view (`PreferencesStore.savedBrowserViews`, keyed by `LibrarySource.persistenceKey`), falling back to the two legacy layout keys and then `.classic` / `.table` for a playlist.

- **Clicks never prune the set; index and search changes do.** `settleBrowserColumns(from:pruningSet:)` is the one place columns are recomputed. ⌘A on the Album column deliberately selects albums outside the anchored artist, so a click only fills missing anchors to its right; a rebuilt or filtered index also drops rows the user can no longer see.
- **A multi-selection resolves literally.** `BrowserCascade.selectedTracks` ignores the anchors on either side of the column that owns the set — otherwise the track anchor would shrink ⌘A to one song. Without a set, the anchors narrow all the way down, and a view ending on an album or a genre resolves to that leaf's tracks (`leafTracks`).
- `visibleAlbums`, `visibleTracks`, `browsingTracks`, `selectedArtist/Album/Track` are the compat surface: each reads its column's content when the view has one and derives from the other anchors otherwise, which is how the inspector and the condensed browser keep working in a `Genre · Track` view.
- Anything that selects from outside the columns (Go to Current Song, the gallery, a version row's menu) goes through `revealTrack` / `revealAlbum`, which set every column's anchor from the track. Do not write `selectedArtistID = …` for that: in a view with no Artist column it has nowhere to go and is a silent no-op.
- **`BrowserEmptyKind`** (Core) decides which empty state the browser draws: an empty Prep Crate, an empty named crate, a disconnected library, and no library at all are different messages, not one generic "no library loaded." It carries its own small `Source` mirror of `LibrarySource` (`.localAll`/`.localCrate`/`.prepCrate`/`.other`) because Core cannot depend on the app target that defines the real enum.

### Search (`index` vs `browsedIndex`)

**`index` is the truth; `browsedIndex` is what the browser draws.** A live search prunes the second (`LibraryIndex.filtered(by:haystacks:)` against `BrowserState.filter`) and leaves the first alone, so conversion, queueing, relinking, batch artwork and the sidebar counts keep seeing the whole source. Only the browser's own lists (`visibleArtists`, `allAlbumsSorted`, `flatTracksSorted`, `browsedPlaylistTracks`), its anchors (`selectedArtist`/`selectedAlbum`), its select-alls and its counts read `browsedIndex`. Adding a reader is a decision: "should a search narrow this?"

- **`BrowserFilter`** (in `BrowserState.swift`) owns what a query means: whitespace tokens, case- and diacritic-folded, every token matching at least one of title / artist / album artist / album / path / format. Pruning keeps an album whole when the album itself matches, and an artist whole when the artist does.
- **Folding is the expensive half.** `LibraryIndex.searchHaystacks(for:)` pre-folds one string per track; the view model builds it on the first keystroke of a search and drops it in `index`'s `didSet`. Without it a keystroke costs ~150 ms at 14k tracks, with it ~25.
- Anything that hides rows must call **`BrowserState.reanchor(in:)`** (the filter setter and `selectSource` both do): it moves anchors onto surviving rows and clears the multi-selection, so nothing invisible stays selected and convertible.
- The field can be put away with the magnifier key in the browser well header (`showSearchField`, persisted, visible by default). Hiding it clears the query with it: a browser filtered by a field that is not on screen reads as a bug. ⌘F brings it back and focuses it.
- **A live search carries across the local library.** `LibrarySource.keepsSearch(movingTo:)` is the rule: crate ↔ crate ↔ All Records ↔ Prep keeps the query, anything else (CD, playlist, remote, device, radio) drops it in `selectSource`. That is what makes the sidebar a map — while a query is live every crate row shows its match count (`crateMatchCounts`, dimmed at zero) and clicking one arrives with the query still applied. Widening the scope is just a switch to `localAll` under the same rule; `LibraryViewModel+Search.swift` is the whole seam.
- **Clearing the filter must recompute.** `selectSource` assigns the new `index` first, and its `didSet` prunes with the filter that is about to be dropped, so `clearSearchState()` recomputes rather than leaving the browser drawing a dead query's results.

### The library data model & index

- The atomic unit is **`LoadedTrack`** = `AudioTrack` (file + tags surfaced for display) + `ConversionMetadata` (the editable/writeable tag set). Defined in `LibraryScanService.swift` and `ConversionModels.swift`.
- A flat `[LoadedTrack]` is turned into a browsable **`LibraryIndex`** (Artist → Album → Track) by `LibraryIndex.build(from:)`.
- **Critical invariant:** grouping into albums uses `OutputPathPlanner.albumFolderKey(for:)`. The browser index, the conversion output planner, and the per-album review sheet **all reuse this same key** so they agree on "what an album is." If you change album grouping, change it there.
- **One album folder is one album.** `albumFolderKey(for:)` reads one file's tags literally, and three ordinary tag inconsistencies each shatter a release into albums that then sort apart: a disc suffix in the title (`Album (Disc 2)`), per-track artists on a compilation or soundtrack with no album-artist tag, and tracks carrying different years. `OutputPathPlanner.albumFolderKeys(for:)` takes the whole set and reconciles it: files sharing one album folder (disc subfolders folded into their parent by `albumSourceFolder(for:)`) and one disc-stripped title get a single key — one artist bucket (the album-artist they agree on, else Various Artists) and one year (the one most of them carry). `LibraryIndex.build` and `MetadataMatchService.partitionByAlbum` both key off it; the per-track function stays for callers that genuinely have one file. Untitled files are deliberately left alone, or a flat folder of loose tracks would collapse into one "Unknown Album", and the stripping is scoped to same-folder groups so a box set's separately-filed discs keep the titles that tell them apart.
  - Every batch planner passes the reconciled key down: `planDestination(…, albumKey:)` and `buildOutputSubpath(…, albumKey:)` take one, and when given it the album-artist / album / year **folder tokens** read the album's identity instead of the file's tags — so conversion, the album-folder review sheet, the convert-queue preview, CD ripping and external-device transfers all write one folder per album. Both parameters default to nil, which is the old per-track behaviour and the right answer for a caller that genuinely holds one file (`plannedOutputName` without a queue).

### Sources model (Crates, Prep Crate, Remote, CD, Playlists, Radio)

`LibrarySource` (enum in `LibraryViewModel.swift`) selects what's shown — cases: `localAll`, `localCrate(name:)`, `prepCrate`, `remote`, `playlist(name:)`, `cd(volumePath:)`, `device(volumePath:)`, `offlineDevice(profileID:)`, `radio(category:)` (the category is optional: nil means All Streams). The view model keeps separate cached indexes (`localIndex`, `remoteIndex`, `cdIndex`, `playlistIndex`, `prepCrateIndex`) for fast switching via `selectSource(_:)`.

- **Crates** are the persistence unit, stored in a user-chosen "Crates Index Folder". A crate is a **`.cdcrate` file = a JSON array of file paths** (membership only). The tracks themselves live once in a **shared `TrackStore`** (`library.cdtracks` in the same folder), and artwork lives in `ArtworkStore` keyed by SHA-256 — `ArtworkAsset.encode` deliberately omits the image bytes, so no index file ever carries base64 artwork. `loadCrateTracks`/`saveCrateTracks` are the I/O; a "Personal Crate" is auto-created. Legacy `.cdlib` files (full `LoadedTrack` arrays with embedded art) are migrated once on launch by `migrateLegacyCratesIfNeeded` and renamed `.cdlib.bak`.
- **A library on an unplugged drive is read-only, not empty.** `LibraryLocation` (Core) decides `notChosen` / `available` / `disconnected` from the bookmark, the mounted volumes and the folder recorded with the local copy; `libraryLocation` is stored on the view model, set at the top of `refreshAvailableCrates()` and on every mount/unmount (`LibraryViewModel+LibraryLocation`), and `cratesDirectoryURL` reads it. Disconnected means the index loads from `LibraryIndexCopy` (`Application Support/CrateDigger/LibraryCopy`, refreshed at launch, quit and will-unmount, swapped in whole), and every action that writes the index or an audio file starts with `guard !refuseWhileLibraryDisconnected()`. **A new writer needs that guard**, or it writes into the copy. The old silent fallback to `Application Support/CrateDigger/Crates` (plus an auto-created Personal Crate) now only happens when no folder was ever chosen. **New index file types go in `LibraryIndexFiles`**, which both `moveIndexFiles` and the copy read. Design: `docs/superpowers/specs/2026-09-16-offline-library-design.md`.
- **`saveCrateTracks(_:name:persistStore:)` re-encodes the whole store.** Pass `persistStore: false` inside multi-crate loops and call `persistTrackStore()` once at the end, or a batch operation freezes the UI at library size.
- **Listening history** is a third store in the same folder: `library.cdplays`, a path-keyed `[String: ListeningStats]` holding play count, skip count, last played, date added and rating. Deliberately NOT a field on `LoadedTrack`: `TrackStore.upsert` replaces whole records and the retag, relink and rescan paths all rebuild one, so stats living there would be one forgotten line away from being silently zeroed. Anything that changes a track's path must call `ListeningStore.repoint(from:to:)` alongside the `TrackStore` update — the same choke points already do both. Plays are counted against `PlayThreshold.isPlayed`, which is also what triggers a Last.fm scrobble, so the two can never drift.
  Since 2.0 beta 9 each record also carries `playsByMonth`, a `"YYYY-MM"` → count histogram written by `recordPlay(at:)` and omitted from the file when empty. It is deliberately a histogram, not a date log, so the file is bounded by tracks × months. `playCount` predates it and stays the lifetime truth: the STATS screen's All Time reads `playCount`, Month and Year read the histogram, and the two are allowed to disagree. `ListeningSummary.compute` is the one reader; the view model runs it only while the STATS screen is showing and something changed.
- **Resume** is a `PlaybackSnapshot` (loaded track plus up to 500 following, position, source key) kept in `PreferencesStore.playbackSnapshotData`, saved by `LibraryViewModel+Resume` on index change, pause, queue edits and at quit, and written only when its bytes changed. At launch `PlaybackSnapshot.resolve` drops paths the `TrackStore` no longer knows and gives up entirely if the loaded track is gone or its file is not on disk. The position lands through the same `pendingSeek*` pair Record Divider uses.
- **Prep Crate** is the staging area: newly scanned folders land here first (`handleImport`), not directly into a saved crate.
- Editing a track's tags (or moving/consolidating the library) must **repoint every crate that references it**: `updateTrackURLInIndex` for one track, `updateTrackURLsInIndex` for a batch (loads/saves each crate at most once, and is what `moveLibrary` and `consolidateLibrary` both funnel through). These also drop the dead old path key from the `TrackStore`. Forgetting this leaves crates pointing at stale paths.
- Remote = Subsonic/Navidrome (`SubsonicClient`); CD = `CDRipperService`; Playlists = M3U via `PlaylistService`; Radio = YouTube streaming (see below).
- **External devices** (`.device`) are mounted removable volumes (`DeviceDetectionService`) that match a saved `ExternalDeviceProfile` — random drives never reach Sources. Matching is `ExternalDeviceProfile.match(_:in:)`: a stored `volumeUUID` is **authoritative** when both the profile and the volume report one, so two iPods that both mount at `/Volumes/IPOD` named "IPOD" stay distinct; profiles saved before UUIDs (or volumes reporting none) fall back to mount path, then name. Legacy profiles self-heal via `backfillVolumeUUIDs` on first connect.

### Device transfers (review, resolve, execute)

Every way of sending music to an external device (copy-mode, the convert hand-off, the offline queue and its SYNC) runs one sequence, and nothing writes to a device outside it. The logic is Core's `Services/DeviceTransfer/`; `LibraryViewModel+DeviceReview` (the sheet and the stores), `+ExternalDeviceTransfer`, `+DeviceSync` and the device section of `+Conversion` only wire it. Before this, copy mode wrote ` (2)` beside whatever was there, convert mode asked Skip/Overwrite by exact path, and SYNC skipped by exact path, so a format upgrade was never seen as one.

**The sequence: review, resolve, executor.**
1. **Review.** `reviewedDevicePlan(tracks:profile:mountedRoot:catalog:…)` runs `DeviceTransferMatcher` against the device's catalog and `DeviceTransferResolver.review` against its files, then shows the "Already on <device>" sheet (`DeviceReviewSheetController`, an AppKit sheet presented from the root) only when an album needs an answer. The sheet is the only place a differing album is decided; Cancel there writes nothing, New and Gaps included.
2. **Resolve.** `DeviceTransferResolver.resolve(review, decisions:)` turns the answers into a `DeviceTransferFilePlan`: every copy and every deletion, decided. It throws (`ResolveError`) if the review was built from albums alone, or for another volume, music folder or transfer settings than the plan is being run against.
3. **Execute.** `DeviceTransferExecutor` runs the plan: all copies first, then the deletions, every write and delete through `DeviceTransferDoor` (one `DeviceFileExecutor` session, see PodBox and the device write door). Converting paths use its `stagedJobs` / `finishConverted` around the ffmpeg batch: ffmpeg writes into a staging folder on the Mac and the finished files are copied onto the device through the door. `DeviceTransferSummary.statusLine` ends every path with the same line (copied, already there, albums finished, replaced, kept both, left alone, failed).

**The matcher's identity rule.** An album is `DeviceAlbumIdentity`: artist bucket plus album title, case- and diacritic-folded, disc suffix stripped, built from `OutputPathPlanner.albumFolderKeys(for:)` so it agrees with the browser. **Year is not part of it**: a remaster meets the copy already on the device and is asked about, not copied in beside it. Tracks match by slot (disc or 1, track number); when either side has no number, by folded title; never by file name, which is what makes MP3 to FLAC an upgrade. When several device tracks share a slot (an MP3 and a FLAC left by older upgrades), the one in the sent track's form pairs first, then the same format, then the first by path, so scan order never decides. **Untitled albums are not an album**: files with no album tag share the "Unknown Album" identity (`DeviceAlbumIdentity.isUnknownAlbum`), and loose singles all carry track 1, so for that identity tracks pair by folded title only, art is compared track by track, and it is never `.differentRelease` (by title or by totals); a single the device lacks is a gap or New, never a Replace of forty unrelated ones. An album is `.new`, `.present`, `.gaps` (fill the missing tracks, silently, into the device's existing album folder) or `.differs` (the sheet). Differences are `DeviceAlbumDifference`: audio form (copy-mode devices only; on a convert-mode device every file is written at the profile's format, so a form difference could only be a settings change and is never compared), art size, a different release (a title at a shared slot, or disagreeing track totals), and `.pathTaken`, which only the resolver sets: a destination that New or Gaps would write is held by a file nothing matched (flat layouts, a stale catalog). It goes to the sheet; nothing ever lands on it silently and nothing gets a silent ` (2)`. The sheet has no pre-selected answer. Replace swaps counterparts for an upgrade but removes the whole device album for another release; Keep both writes a sibling version folder (`Kind of Blue [2]`, `OutputPathPlanner.nextAvailableVersionFolderName`; a ` (2)` file name in flat/sourceRelative layouts); Leave it is remembered per device and identity in `DeviceLeftAloneStore` (`Application Support/CrateDigger/DeviceLeftAlone/<profileID>.json`), brought back by the sheet's toggle and forgotten in Preferences ▸ Devices. A Leave it for an album whose only difference is `.pathTaken` is not remembered (`record(_:kinds:profileID:)`): it says nothing about the album, and remembering it would silently leave alone a later real upgrade. A stored answer (a sync queue entry's `DeviceStoredDecision`) carries the `DeviceDifferenceKind` it answered and applies only to that kind.

**Rules a change must not break.**
- **A new device writer goes through `reviewedDevicePlan`, then `resolve`, then the executor, and ends in `patchDeviceCatalog`.** Not through `ExternalDeviceTransferPlanner` with `avoidExistingFiles`, not through a bare `FileManager.copyItem` (it leaves `._` twins on FAT and skips the write policy). `naturalNames` on the planner exists for the resolver; a caller that passes it itself is writing without the review.
- **Deletions are only for albums whose writes all landed, and never after a cancel.** `DeviceTransferFilePlan.deletions(afterFailing:)` drops the deletions of any album with a failed copy; a cancelled run keeps every old file (`cancelledDeletionReason`). Write first, delete after, so an interrupted transfer never leaves an album with neither. Deletes remove the matcher-attributed audio files of the replaced device copy, not other files in the folder, and delete rather than trash (a Trash on a removable volume is `.Trashes`, still taking space).
- **Nothing is read from the catalog, written, versioned beside or deleted outside the profile's music folder.** When the music folder is the volume root, dot-folders and `iPod_Control` are outside it too. This is what protects backups and the stock iPod database; the cost is that an album kept elsewhere on the device reads as New.
- **Nothing is half-written under a final name.** The door writes to `<name>.cdtmp` beside the destination, flushes it and renames it onto the name (`rename(2)`; the old `.cdpart` partials are gone). A file that was not there must still not be there at the rename (`exclusive`), so one that appeared after the review fails that one item (`DeviceTransferDoor.appearedReason`). A folder is created only when a write into it starts and removed again if the write failed and left it empty. A leftover `.cdtmp` from a crash is cleared only when the journal says an earlier session on that volume announced it.
- **Art is compared by pixel size, never by hash.** A conversion re-encodes art, so a hash differs every time. What a transfer would leave behind is `DeviceWrittenArt`, shared by the matcher and the catalog patch so they cannot disagree about one write; embedded art outranks the folder `cover.jpg` on read-back, as the device scan reads it. Raising or lowering a profile's art cap therefore still reads as an art difference; that is known and accepted.
- **Recorded art sizes are pixels, and the review measures what it sends.** Every producer of `ArtworkDimensions` reads the image header (`ArtworkQuality.pixelSize(ofImageData:)`, `ArtworkService.pixelDimensions`), never `NSImage.size`, which is points: a 1400 px cover tagged 300 dpi used to record 336 and read as differing after every real scan. Library records made before keep points until rescanned, so `reviewedDevicePlan` measures each distinct cover sent (`ArtworkService.pixelSizes(of:)`: full-resolution bytes only, header only, once per hash, off the main actor) and passes them to `review(…, artPixelSizes:)`, which substitutes them on the tracks sent (`DeviceWrittenArt.measured`); the plan's copies carry the measured tracks to `writtenTrack`. The on-disk `ArtworkStore` holds 512 px thumbnails and must never stand in for full-resolution bytes: `dataCache` is full resolution only (store thumbnails go to their own cache), because `hydrated`, `storeData` and `pixelSizes` all trust it.
- **The catalog is patched, not invalidated.** After a write, `patchDeviceCatalog(for:adding:removingPaths:)` adds the written files (`DeviceCatalogStore.writtenTrack`, tags from the source plus the output format) and removes the deleted ones, so the offline queue has a last-known catalog to compare against. Every catalog write goes through `DeviceCatalogWriter`, which refuses a whole-volume scan's save when a patch or removal moved the key's token on since the scan started; otherwise a late browse scan puts back what the transfer just corrected. `invalidateDeviceCatalog` is for writes a patch cannot describe (FIX ART) and for RESCAN. Without a saved catalog a transfer scans the device first, with the same whole-volume scan browsing uses. Two kinds of saved catalog count as missing: one from an older format (`DeviceCatalogStore.formatVersion`; the transfers before format 2 never patched the catalog, so everything they wrote would read as a name taken by an unknown file) is dropped once at launch by `discardOlderFormats`, and one saved while the device mounted elsewhere (`/Volumes/IPOD`, now `/Volumes/IPOD 1`) fails `DeviceCatalogStore.describes(_:deviceAt:)` and is walked again rather than having every track filtered out as outside the device. Bump the format version when a change makes saved catalogs untrustworthy.
- **The device is busy until the catalog is patched.** `isDeviceTransferRunning` (not `conversionProgress.isRunning`, which a copy or SYNC never sets) covers renames, deletions, covers and the patch; GO, the Cancel key, ⌘. and the busy job all read it. A convert run sets its Cancel target (`activeConversionService`) the moment it reads as busy, so an early press is not dropped; SYNC has no cancel, so the Cancel key is dimmed and ⌘. disabled while it runs (`canCancelConversion`). The device must be the mounted volume that holds the profile's root (`MountedDevice.containing`), or the transfer stops with an alert before anything is read.
- **SYNC converts one job per call, on the Mac: `ConversionService.runSingle`.** `enqueue` appends to the service's queue and `runQueuedJobs` reruns the whole queue, so on the one service SYNC shares entry k reran jobs 1 to k, read `results.first` (the wrong job's), left stray partials and could rename a truncated one into place and then run the Replace deletions. `runSingle` runs exactly the job it is given and returns its own result, honouring `cancel()`. A new caller that converts file by file on one service uses it; the batch `runQueuedJobs` is for callers that convert a batch once. SYNC stages each entry in a per-run folder on the Mac under the destination's own name and extension (`DeviceSyncQueuePlanner.conversionStagingURL`; never the queued bake's, or ffmpeg picks the wrong muxer), then copies it over through the door.
- **Queuing reviews against the last-known catalog with the staging tree standing in for the device** (`DeviceSyncQueuePlanner`, `catalogOnlyFileManager`); SYNC reviews the queue again against the device itself and shows the sheet again for any album that now differs and has no stored answer. A queue-time `pathTaken` answer is not stored: a staged file clash says nothing about the device.
- **Cancel and a refusal write nothing.** Leave-it answers are recorded only after the preflights (writability, free space) pass, never for a send that did not run.

**Record Divider on a device run.** The review compares whole tracks and plans one file per source, but a divided recording is one file per marker, all cut from one source; `DeviceRecordSlices` plans those apart at their natural paths and merges them into the reviewed plan. A slice already on the device is left and counted as already there, never overwritten.

**Folder art is a switch, and the art mode is stored per device.** `ExternalDeviceTransferSettings` carries `writesFolderCoverArt` and `artworkMode`; `usesFolderCoverArt` reads the setting, not the device kind. Profiles saved before either key decode to what they did before (a Rockbox iPod: Strip plus folder art; otherwise Keep when there is no art cap, else Re-embed, folder art off), and choosing the Rockbox kind for a profile turns folder art on and moves the art mode with it, both ways. The switch is independent of the art mode, so every path (mounted convert, bake, SYNC) reads `artworkMode` from the profile instead of deriving it from the folder-art flag. It is edited in Preferences ▸ Devices and in a Folder Art row on the CNVRT Patch Bay (`ConversionOptionsSelection.seeded(from:)` seeds the cockpit from the profile, `ConversionOptionsSelection.deviceTransferSettings(over:)` is the inverse that `persistSelectionToDevice` saves). The cover is `cover.jpg` at `FolderCoverArtWriter.defaultMaxDimension` (400 px). The DEVICES screen's Artwork cell is Core's `DeviceArtworkReadout` and says both when art is inside the files and a cover sits beside them. Ordinary (non-device) conversions got the same switch, default off.

**Who may replace a cover.** A device run writes the cover of every album folder it wrote into, replacing what is there, except a folder that only took Gaps fills: the user did not choose to change that album, so `DeviceTransferFilePlan.coverFolders(after:hasCover:)` keeps a `cover.jpg` it finds there and writes one only where there is none (copy, convert and SYNC all go through it). An ordinary conversion never replaces a `cover.jpg`: `FolderCoverArtWriter.conversionCovers` skips a folder that already holds one, the destination root in flat mode, and a folder the batch puts more than one album into. **FIX ART only adds**: `FolderCoverArtWriter.fixArtPlan` keeps every album folder that already has a cover (`hasCover`, case-insensitive from the folder listing) out, the confirmation and summary give both counts (`FixArtText`), and it writes through `DeviceTransferDoor.writeCover(_:to:replacesExisting: false)`, which leaves any file already at the name, CrateDigger's own included. Replacing each cover with a 400 px re-encode of itself only lost quality.

**Checking it.** DEBUG `CRATEDIGGER_DEVICE_REVIEW=1` (or `answered`) opens the review sheet with fabricated rows for every kind of difference, so it can be captured without a device; nothing is written whatever the answer. Never test a transfer against a real device: tests use temp directories.

### PodBox and the device write door

PodBox is a Rockbox firmware for iPods that keeps its own library from the files on the disk. Two things follow for CrateDigger: a stray macOS `._` file on the FAT volume is scanned as music, and the player finds artist pictures by *name*, so the file CrateDigger writes must be named the way the player will look. Everything here is Core (`Services/DeviceFiles/`, `Services/PodBox/`, `Models/DeviceFirmware.swift`, `Models/PodBoxPreferences.swift`) plus `LibraryViewModel+PodBox` and `+ArtistPictures`. Design: `docs/superpowers/specs/2026-11-11-podbox-integration-design.md` (its Status section says what is built); the owner's checks on the real iPod: `docs/PODBOX_CHECKS.md`.

**Firmware is probed per mount and never saved; there is no new device kind.** `DeviceFirmwareProbe.probe` reads a fixed list of small files under `.rockbox/` (each with a size cap, opened for reading only, after `attributesOfItem` says regular file, so a FIFO cannot block it) and returns `DeviceFirmware`: flavour (`podBox` when `library/format.dat` starts `LYOT`, or the folder holds PodBox's setup files but the player has not started on them yet; `stockRockbox` with a `rocks/` folder; else `unknownRockbox`), library layout (the header's u16, checksum deliberately not verified because the real device's is `FF FF FF FF`), the build, the layered settings (`PodBoxConfig`: PodBox's defaults, then `default-config.cfg`, then `config.cfg`), the `/<HDD0>` path prefix, and the count of `._` lines in `unreadable.txt`. `DeviceCapabilities(firmware:fileSystem:)` turns that and the volume's file system (`msdos`/`exfat`) into what may be offered. A profile stays a `.rockboxIPod`; `LibraryViewModel.deviceFirmware` holds the probes. **Mounting only reads** (spec invariant I6): `DeviceSessionGate` is the table of action by trigger by UUID match (`.mount` allows `.probe` and nothing else; a user action may transfer and sweep for any matched profile and write extras only for a device matched by volume UUID). A never-booted PodBox keeps its file features (pictures, playlists); a layout above the known one (`DeviceFirmware.knownLayout`, 5) says so instead of guessing.

**One door for every byte written to a device.** This is the rule the rest of the section exists to keep.
- **`DeviceWritePolicy`** (pure) is an allowlist by role (`DeviceFileRole`: audio, cover, temp, artistPicture, artistFolderPicture, and the later roles that no writer enables yet), each with its own area and name rule; a role the caller did not enable is refused, which is how a phase or a manual check gates a writer in one place. It refuses: the player's trees (`.rockbox`, `.rockbox_backup`, `.backup`, `iPod_Control`, `.Trashes`, `.Spotlight-V100`, `.fseventsd`) at **any path component**, and `.scrobbler.log`; empty, absolute, `.`/`..` paths and any path whose resolved real path leaves the volume; any component ending in a dot or a space, or holding `~<digit>` (FAT drops the first and aliases the second, so they can name another file than they read as); `._` names. Keys are NFC, case-folded through `uppercased().lowercased()` and trimmed of trailing dots and spaces, and the journal uses the same key. A delete is allowed only for a reason (`DeviceDeleteReason`): a proven `._` twin of a *media* file, a file the journal proves ours, an audio file the user chose to Replace, a stale `.cdtmp` the journal announced.
- **`DeviceFileIO`** holds the primitives (data-only `copyfile`, atomic write through a flushed `.cdtmp` and `rename`, attribute stripping, remove, the AppleDouble proof). The copy and write primitives never delete a twin. **`DeviceFileExecutor`** is the only caller of the mutating primitives, and for each operation it checks the volume (the root's device and inode as captured at init, a real mount point, the expected volume UUID), the policy for the file and its temp both as given and after resolving symlinks, room (the size plus 8 MB), then the journal. Identical bytes are `unchanged` (dates untouched). A file it did not write is `refusedForeign`; the one exception is a cover in a folder the same transfer wrote tracks into (`replacesForeign`), and an audio file the user chose to Replace (`replaceAudio`, no ownership proof and no backup, as for its delete). Everything it replaces or deletes is backed up on the Mac first. On `msdos`/`exfat` it also removes the provenance twin each of its own writes just made (below). The volume UUID is read fresh before every operation (`systemVolumeUUID`: a new URL from the path with its resource cache emptied), never from values Foundation cached on a kept URL.
- **`DeviceWriteJournal`** (`Application Support/CrateDigger/DeviceJournal/<profileID>/journal.jsonl`, backups under `backups/<session>/<path>`; one shared instance per profile) is the proof of ownership. Every session that can replace or delete keeps its ID, logs its backup folder (session ID public, path private) and, in the summaries of Clean Up Mac Files, FIX ART and Remove artist pictures, offers **Show Copies in Finder**, enabled only when `backupFolderIfUsed(sessionID:)` says the session kept a copy (`AppAlert.withSecondary`). The journal: a record per write with size and SHA-256 (none for audio), the volume UUID and a `subject` (whose picture it is). A file is ours only when the journal's last act on that key *on this volume* was a write and the bytes on disk still match; a half-written journal line reads as not ours, the safe way to be wrong. A `tempIntent` record is written before a session's first write so a crash's `.cdtmp` can be cleared later and nothing else is.
- **`DeviceTransferDoor`** is the transfer's face of the executor (copy audio, delete what the user chose to Replace, write a cover): one door is one session ID. The device review, resolve and execute sequence above is unchanged; it just writes through here.
- **A new device writer** checks `DeviceWritePolicy` (enable its role in `devicePolicy(for:firmware:)`), writes through `DeviceFileExecutor` or `DeviceTransferDoor`, joins `isDeviceBusy`, and ends with `finishDeviceSession`. Never a bare `FileManager` call on a device path. `FileManager.copyItem` is banned there in particular: on FAT it carries the source's attributes, so macOS makes a `._` twin of every file it copies, which PodBox then reads as an unreadable track. The door's data-only copy carries none, but that alone does not prevent twins (next point).
- **The provenance twin.** macOS tags every file and folder an assessed app creates (a notarized download is assessed) with `com.apple.provenance`, which no one can remove. On FAT the kernel stores it in a `._` twin, so in a shipped build *every* file and folder the door writes (`._Music`, `._Beach House`, `._01 - Zebra.m4a`, `._cover.jpg`) gets one, data-only copy or not; a fresh `swift build` in a worktree is untagged and shows none, which is how it went unseen. So the executor, on a volume whose file system is `msdos` or `exfat` (read once at init), removes the twin *its own write just made*: for a file landing by rename `._<name>` (and `._<name>.cdtmp` if one survives the rename), for each folder it creates that folder's twin, outermost first and the deepest last, right after the `mkdir`. Only when all hold: nothing was at the twin's name before this write (checked with `lstat` before writing; the rename moves a temp's twin onto the target's, so a twin at the temp's name rules out both); it is a regular file, not a symlink, 26 bytes to 128 KB, AppleDouble (magic `00 05 16 07`, version 2); and `AppleDoubleFile` (Core, the parser of the entries and the `ATTR` block) finds no attribute but `com.apple.provenance`, Finder info all zero, no entry but Finder info and the resource fork, and no resource fork beyond the empty 286-byte placeholder macOS writes. The bytes, device, inode and size are re-checked right before `unlink`, as the sweep does (`DeviceFileIO.removeProvenanceTwins`, which only `DeviceFileExecutor` may call). Not journalled (it is the write's own by-product), logged at debug level, private, and never fails the write. **Every other `._` file stays the sweep's business**: one that was there before, or carries anything else. Two kernel facts measured in the FAT sandbox: `rename(2)` moves the source's twin onto the destination's and, where the source has none, deletes the destination's; `unlink` and `rmdir` remove a twin with its file. Tests must not assume the process is untagged: they assert "no attribute other than `com.apple.provenance`", and the sandbox tests stand in for a tagged process by setting the attribute themselves (`tagAsProvenance`), so the kernel writes the real twin either way.
- **`DeviceWriteDoorLintTests` enforces it by reading the sources.** Rule 1: the guarded folders (`Services/DeviceFiles`, `PodBox`, `DeviceTransfer`, `FolderCoverArtWriter.swift`, `UI/ExternalDevices`, and the convert-to-device path in `UI/Conversion/LibraryViewModel+Conversion.swift` and `UI/Carbon/Library/LibraryViewModel.swift`, whose Mac-side staging and library-index writes are each allowlisted) may not call a file-system mutator (Foundation, POSIX, streams, image/audio writers, `Process` launching `rm`...). Rule 2: nothing in `Sources` may call the door's own mutators except `DeviceFileExecutor.swift`. A line that really writes on the *Mac* (the journal, the picture cache, a staging folder) goes in `allowedLines` with its reason; each entry must match exactly one line, so a stale entry or a second write added beside it fails the test. The lint is crude on purpose and fails toward flagging; add an entry rather than weakening a rule.
- **`FakeIPod`** (test helper) builds a temp-dir replica of the device, and `assertPlayerStateUntouched()` compares a manifest of the protected trees before and after: **every writer test ends with it.**
- **Known gap.** The door covers transfers, SYNC, covers, cleanup and artist pictures. Ordinary conversions and CD rips whose output folder is a device, Record Divider exports there, and Edit Tags, art embed/strip, Move to Trash and artwork-manifest saves on a browsed device still write outside it (existing features, not changed). `MountedDevice.profileDevice(holding:in:profiles:)` (Core) answers "is this URL on a profile device" for whoever routes them.

**FAT-safe names.** `FATName.component(_:extension:)` makes one path component FAT can hold: NFC; `?` and `*` removed; `"` becomes `'`; `< > | / \ :` become `-`; control characters `_`; leading dots removed; trailing dots and spaces trimmed; a reserved stem (`CON`, `COM1`...) gets a trailing `_`; cut to 255 UTF-16 units on a grapheme boundary keeping the extension. `fitsPlayerPath` is the 252-byte limit counted with the `/<HDD0>` prefix. **The trailing-dot rule is load-bearing**: the policy refuses a component ending in a dot, so a transfer must sanitise first. `ExternalDeviceTransferPlanner.deviceSafeURL` applies it (and drops a `~<digit>`) to every component of a device destination before the policy sees a path, so `R.E.M.` is written as `R.E.M` and a new album never fails. Existing folders that already end in a dot are refused by the policy: gap fills, Replace and covers there fail with a message instead of writing, and a Gaps fill into a refused folder fails the whole album rather than splitting it.

**The `._` sweep.** `AppleDoubleSweeper.plan` walks and reads 8 bytes per `._` file, deletes nothing, and plans only on `msdos`/`exfat` (on APFS or HFS+ a `._` file is something a user made). The proof, all of it: the name starts `._` and is longer than that; `lstat` says regular file; 26 bytes to 128 KB; bytes 0 to 7 are `00 05 16 07 00 02 00 00`; the name after `._` has a media extension (`DeviceWritePolicy.appleDoubleMediaExtensions`, the policy's own list so the plan never lists a twin the executor would refuse); no player tree in the path. Twins of non-media files are left alone and counted (`leftAlone` by reason). The executor re-proves at the moment of deletion through one descriptor, backs up *from those bytes*, and re-`lstat`s (device, inode, size) immediately before `unlink`, so a file swapped in between survives. Two ways in: the user-started **Clean Up Mac Files…** (device context menu, folder context menu, Preferences ▸ Devices), which confirms with the counts and is the owner's check M4's tool, and the **automatic clean-up after each transfer**, which is `PodBoxPreferences.appleDoubleCleanup`, **off by default per device** until the owner has run M3 and M4 on that iPod; it sweeps exactly the parent folders the session wrote or deleted in, non-recursively. Preventing new twins (data-only copies, no extended attributes, and removing the provenance twin of each door write, above) needs no switch and is always on.

**The session gate and `isDeviceBusy`.** `isDeviceBusy` (`LibraryViewModel+PodBox`) is the one truth for "a device is being written": a send or convert run through its catalog patch and `finishDeviceSession` (artist pictures included), SYNC, Clean Up Mac Files, FIX ART, and artist pictures written or removed on their own. **Every device writer checks it before starting and joins it**, and both Eject paths check it; two writers interleaving would also interleave journal appends. Check it *before* an `await`, not after. `finishDeviceSession` runs after `patchDeviceCatalog` on every write path: the (switched) sweep, artist pictures when allowed, then the next-step lines (`PodBoxNextSteps`: eject, Update Database, Update Art Cache; plain "Eject the device" for other Rockbox). It never fails the transfer. Music never waits on garnish.

**Artist pictures.** PodBox shows a person's picture when a file or folder name keys to the person's name, so CrateDigger must compute that key exactly as the player does.
- **`PodBoxArtName` is a port of the player's `art_name.c`, not `DeviceAlbumIdentity.fold`** (a different question with different rules; never swap them). Only letters and digits count; ASCII lowercases; `&` reads as `and`; Latin-1 and Latin Extended-A fold by a fixed table (Ø folds to `o`); combining marks and general and CJK punctuation drop; every other script is kept unlowercased; a leading `The ` and trailing `, the` are ignored; a name with one comma also matches reversed (`altKey`); the kept code points are FNV-1a hashed. `scripts/podbox-artname-vectors.sh` regenerates `Tests/CrateDiggerCoreTests/Fixtures/podbox-artname-vectors.json` from PodBox's own C (302 names, all matched); only that output is committed, no GPL source.
- **`PodBoxArtLookup.artistPicture(for:albumFolders:tree:)` simulates the player's own search** against `DeviceArtTree` (one read-only listing of `/Artwork`, the music folder and the folders above it, plus the catalog). The player uses the highest folder named for the person whether or not it holds audio, so the simulation does too. It returns `.none` (the player finds nothing), `.found(path)` or `.uncertain(reason)`. **Only `.none` licenses a write.** Anything the simulation cannot see (a folder never listed, books, a FAT-hidden `Folder.jpg`, a full library-folder table, a catalog that no longer matches the walk, so `plan.refusal`) reads as `.uncertain` and is left alone. `.found` is replaced only when the journal proves CrateDigger wrote it for this same person (its `subject`) and its hash is unchanged. A planner that guesses wrong hides the owner's own picture; leaving a gap is the cheap error.
- **Match rule.** A candidate is `noMatch` unless the player would take its name for ours; `confident` when one of its album titles equals one of ours after dropping trailing `(...)`/`[...]` and folding; `uncertain` otherwise. Self-titled and generic titles (`Greatest Hits`, `Live`, `Gold`...) never confirm. The finder takes a picture only when exactly one candidate of a source is confident and its image prepares; two confident candidates are held for the owner. Uncertain candidates (at most five) go to the sheet. **Becoming the default is stricter** (`ArtistPhotoTrust`, read by the lookup run and by `ArtistPictureSession.vetted`, which every store of findings goes through, the sheet's Find and a transfer's alike): under a confirmed identity a Commons pick must be that MusicBrainz artist's (`sourceID`) and any other must fold equal to the confirmed name; under any other identity it needs two shared telling titles (`ArtistPictureFinding.sharedTitles`). Anything else is held as a candidate (a CHECK row), so a namesake's picture never reaches the iPod unreviewed.
- **The picture is the artist's default photo** (see Artist profiles below). `ArtistPictureSession.pictures(profiles:cache:)` gives the planner a lazy provider (`ArtistPicturePlanner.Pictures`: a cheap `has`, and `bytes` asked only for an artist it is about to write or compare) from each artist's `defaultPhotoRef`, prepared by `ArtistPictureImage.prepare` once and kept by photo hash in `ArtistPicturePreparedCache` (`Application Support/CrateDigger/ArtistPictureCache/<hash>-400.jpg`), never for `notOnIPod` or `noPhoto`; the sheet's rows, `namesToFind` and the prepared map all read profiles through `ArtistPictureProfiles`, which also matches the player's way (`Frank Herbert` finds the profile kept as `Herbert, Frank`). Only the source of the bytes changed: the planner's rules and the door are as below. The sheet's **Don't Send to iPod** (formerly No Picture) is `notOnIPod`, badge NOT ON IPOD, and hides nothing in the app; the owner's No Photo on the artist page reads NO PICTURE. A pick in the sheet becomes one of the artist's photos and the owner's default (`ArtistPictureRow.apply`; `ArtistPictureEdit.picked` carries the original as well as the 400 px copy); Clear takes back only the sheet's own word (Don't Send, held candidates, the last "nothing found") and never removes a photo, so it is off on a ready row with no pending edit.
- **Sources, in order** (`ArtistPictureFinder`): the owner's pick; an `artist.jpg`/`folder.jpg` in a library folder named for the artist; Deezer (`search/artist`, then `artist/<id>/albums`); Wikimedia Commons through MusicBrainz and Wikidata (property P18; the top three MusicBrainz matches scoring 90 or more), with the file's licence and author kept as `ArtistPictureCredit` (the sheet's Find only: the background lookup builds its Commons candidates from its own identity search, see Artist profiles). **What leaves the machine:** the artist name, and the ids and file names the services themselves return, over HTTPS to `api.deezer.com`, `musicbrainz.org`, `www.wikidata.org`, `commons.wikimedia.org` and the pictures' own hosts (`upload.wikimedia.org`, `*.dzcdn.net`; `URLSessionPictureFetcher` fetches nothing else, redirects included). Not a path, a device name, a user name or an e-mail. The client name is the app's generic `CrateDigger/<ver> (https://cratedigger.mrbarkan.com)`, the same for every install, because MusicBrainz and Wikimedia ask for a descriptive one. The iPod side fetches nothing unless the owner turned on `findsArtistPicturesAutomatically` (off) or pressed Find Missing in the sheet; the background artist lookup (Artist profiles, on by default) is what fills most default photos now, and a transfer that may write pictures sends what it found. Bounds: 8 s per artist (30 s in the background lookup) and 120 s per run; a quota answer backs off the run, a transport or 5xx failure stops it. Every Wikimedia request (Wikidata, Wikipedia, Commons, the lookup run's images) waits at one app-wide spacer, `RequestSpacer.wikimedia`, a request a second. A found picture's `ArtistPictureFinding.original` carries the bytes it was prepared from, so whoever keeps it as a photo never downloads it twice.
- **A failure is never "not found".** `ArtistPictureFinding.Outcome.failed` is not storable; a "not found" is trusted for 30 days, so caching a failure would silence an artist for a month. Only `isStorable` findings are kept, by `ArtistPictureSession.store(_:in:now:)` into the profiles: a found picture as a photo (the default only when there is none; never under "no photo" or from a source the owner removed), uncertain candidates as `photoCandidates`, "not found" as `photoSearchedAt` (kept apart from `checkedAt`, the lookup's cursor). **`ArtistPictureStore` (`library.cdartists`) is superseded**: nothing writes it; `ArtistProfileMigration` reads it once when the crates folder resolves and renames it `.bak`.
- **`ArtistPictureImage.prepare`** makes the file: a 400 px square (a portrait keeps its width and the square sits a third of the way down, where a face is), sRGB, baseline JPEG, at most 100 KB, with the Exif/XMP/ICC/comment segments cut out; pixel and byte caps are checked before any decode, and a banner, a thumbnail or a truncated file gives nil. Bytes that already are such a file (`isOutputShaped`) pass through unchanged, so `prepare(prepare(x)) == prepare(x)` and a picture already on the iPod (or a migrated photo) hashes the same and is not rewritten. The old pre-migration cache (`Application Support/CrateDigger/ArtistImages`) is **left in place on purpose**: every crates folder on the Mac shares it, two folders can share one file by hash, and a folder not yet migrated needs its bytes (an owner's pick among them); its files are small 400 px JPEGs. Do not add a clean-up.
- **The `/Artwork` budget.** PodBox holds at most 2,048 files and a 48 KB name pool across `/Artwork/People` and `/Artwork/Covers`, and silently never shows the rest. `PodBoxArtworkBudget` stops at 1,900 files and 44 KB, counting every file already there whoever put it, so the owner's own additions keep room. Destination `.artworkFolder` writes `/Artwork/People/<stem>.jpg` (stem from `PodBoxArtName.fileStem`, FAT-safe and still keying to the name); `.artistFolders` writes `folder.jpg` in the artist's folder.
- **Gating** (`ArtistPictureSession.mayWrite`): the destination is not off, the device is PodBox (`centralPeopleArtwork`), it is matched by volume UUID, and, inside a transfer, the owner has marked check M5 passed on this iPod (`PodBoxPreferences.passedChecks`, Preferences ▸ Devices ▸ Verified on this iPod (M5)). A mount never writes. The Artist Pictures sheet (device context menu, Preferences ▸ Devices) needs the destination on and the UUID match, and its footer gives `mayWrite`'s own reason when it may not write. **Apply is held by M5 too, to one picture**: until M5 is marked passed, `ArtistPictureSession.applySelection` writes at most one artist's picture (the first ready one the owner changed in this sheet session, else the first ready one, most tracks first), leaves the rest ready and the footer says so (`oneFirstFooter`); after M5 it writes every ready one, after a confirmation inside the sheet that gives the count (`applyConfirmation`; the device is planned again at the write). Apply's busy job ends `.failed` when every write failed. "Remove artist pictures CrateDigger added" is a plan of journal-owned deletes (`removalPlan`), backed up first; the owner's pictures stay. A DEVICE row cannot be changed from the sheet (Don't Send to iPod, Choose File and Clear are off, and the row says why); when the journal proves CrateDigger wrote that picture for that person and it is unchanged (`ArtistPicturePlanner.removal(of:forArtist:…)`, the context's `crateDiggerPictures`), the row offers **Remove from iPod** for that one artist, through the door, backed up. A change to pictures or covers sets the DEVICES ticker's "NEXT ON IPOD · UPDATE ART CACHE" and records `stamps.dat`'s modification date as it was then (`PodBoxNextSteps.ArtCacheMark`, only ever `stat`ed); the reminder clears when the stamp differs in any way (`isDone(_:stampNow:)`), so an iPod with an unset clock clears it too. A mark saved by an earlier build has no stamp and keeps the old "newer than the write by a minute" rule.
- **Held candidates persist.** A profile with no picture keeps its candidates (`photoCandidates`, `ArtistPictureRecord.HeldCandidate`: source, id, image URL, credit; never the image), and the sheet shows them as CHECK rows when it opens again. The sheet's Find Missing (`ArtistPictureRow.findTargets`) skips a row with a fresh "not found" (`notFoundAt`: `ArtistPictureProfiles.freshNotFound`, the later of `photoSearchedAt` and a background lookup that left no photo, the same 30-day rule as `namesToFind`), which says so, unless the owner picks **Look Again** on it. Find refuses before any lookup while the library is disconnected.

**The PodBox layout preset.** `RockboxLayoutPreset` (`podBoxRecommended`: `Album Artist / YYYY Album`, since PodBox sorts albums by the year at the front of the folder name; `artistAlbum`; `custom`) *seeds* a profile's `FolderTemplateConfig`; it never changes an existing profile by itself. It seeds only a new Rockbox profile whose probe says PodBox, and choosing one in Preferences asks first when the device already has a catalog. **`FolderTemplateConfig.omitsMissingYear`** drops the `Unknown Year` token when an album has no year, so a yearless album is `Artist/Album`, not `Artist/Unknown Year Album`. It is set by this preset only and encoded only when true: every saved template decodes it false and keeps the paths it always made, because changing them would write an albums already on a device a second time under a new name. **Anything that rebuilds a `FolderTemplateConfig` must carry the flag through** (`ConversionOptionsSelection` does, in `seeded(from:)`, `deviceTransferSettings(over:)` and the conversion view).

**Readiness notes** (`PodBoxAdvisor.deviceNotes`, read-only, shown in Preferences ▸ Devices): Mac files the player is reading as music, artist art switched off on the iPod, a music folder outside the scanned paths, the play log off, names the player cannot key, paths over the limit, compilations with no album artist, embedded-art-only albums, a newer layout, a never-booted iPod. Each can name the menu path on the iPod.

**The FAT sandbox** settles what is about macOS, not PodBox, on a real FAT volume without touching a device. `eval "$(scripts/fat-sandbox.sh up "$SCRATCH")"` makes a 64 MB FAT32 image in `$SCRATCH` (an existing folder outside `/Volumes`), attaches it `-nobrowse` at `$SCRATCH/mnt` so device detection cannot see it and prints `export CRATEDIGGER_FAT_SANDBOX=...`; then `scripts/test.sh --filter FATSandboxTests`; then `scripts/fat-sandbox.sh down "$SCRATCH"` (detaches every attachment of that image, found by `hdiutil info`, and deletes it). It refuses a `/Volumes` path. Without the variable the tests skip. It showed `copyItem` creates `._` twins and the door's copy and ffmpeg do not *from an untagged process*; a tagged one (any notarized build, or a test bundle macOS has assessed, such as the main checkout's) gets a provenance twin for every file and folder whatever it writes with, which the door then removes (`testDoorLeavesNoProvenanceTwinOnFAT`; S1 and S9 print whether the run was tagged). Run it when the door's write path changes, and from a tagged build too.

**DEBUG hooks (none touches a device unless a path says so).** `CRATEDIGGER_PODBOX_DRYRUN=<volume path>` (optionally `CRATEDIGGER_PODBOX_MUSIC`, default `Music`) prints the probe, the capabilities, the cleanup plan counts, the size table and the names section, then `0 files would be written`, and exits; it constructs no executor and no journal (the owner's M1 to M3). `CRATEDIGGER_ARTIST_PICTURES=1` opens the Artist Pictures sheet with twelve made-up artists. `CRATEDIGGER_DEVICE_SUMMARY=1` shows a fabricated device summary with next steps and an Eject key that only logs. `CRATEDIGGER_PODBOX_UI=<mount point>` browses a FAT image attached *outside* `/Volumes` and opens Preferences ▸ Devices; it refuses `/Volumes` and refuses to run unless `CFFIXED_USER_HOME` points at a scratch home. Launch captures of any of these with `CRATEDIGGER_CRATES_DIR` set to a scratch folder, and never attach a profile to a real device. Launching the app unisolated rewrites `~/Library/Preferences/CrateDiggerApp.plist` and the saved device catalogs (a format bump resets them).

**Rules a change must not break.**
- Mounting never writes to a device or to listening history. Nothing in `Services/PodBox` constructs an executor at probe or mount time.
- The denied trees win over any configuration, including an empty music folder.
- A file CrateDigger did not write is never replaced or deleted, except what the user chose to Replace and a cover beside tracks the same transfer wrote.
- A `._` file is deleted only with the whole proof, re-proven at deletion, after a Mac-side copy, and only as the twin of a media file. The one exception is the provenance twin a door write on FAT just made (new at that name, holding nothing but `com.apple.provenance`), which the executor removes with no copy, since it holds nothing to keep.
- Only `.none` licenses writing an artist picture; a failure is never stored as not found; the lookup follows the player, not what looks tidy.
- A path crossing the policy is FAT-safe first. `~<digit>`, a trailing dot or space and `._` names are refused by the policy as the last line, not the first.
- Music never waits on garnish: pictures and cleanup run after the audio and the catalog patch, and their failure never fails or rolls back the transfer.
- A feature resting on something not read from PodBox's source or seen on the device ships behind a per-device switch that stays off until its named manual check passes (`docs/PODBOX_CHECKS.md`).
- The only index file types are in `LibraryIndexFiles` (and the folders that move with them in its `movedFolders`); the journal is Application Support, not the library.

### Artist profiles

Selecting an artist shows an **artist page** in the inspector's INFO tab (portrait, facts, Wikipedia bio, members, genres, library and listening stats), filled in by a silent background lookup and editable by the owner, with any number of photos, an owner-chosen default and an artist photo viewer; the default photo is also what a PodBox iPod gets. Core is `Services/ArtistProfiles/`; the app is `LibraryViewModel+ArtistProfiles`, `ArtistLookupWorker`, `Inspector/ArtistPageView`, `Sheets/EditArtistSheetController` and `Main/Browser/ArtistPhotoViewer`. Design: `docs/superpowers/specs/2026-11-12-artist-profiles-design.md`.
- **Store.** `ArtistProfileStore`: `library.cdartistinfo` in the Crates Index Folder (in `LibraryIndexFiles`, so moves and the offline copy carry it) plus `ArtistPhotos/<sha256>.jpg|png` beside it (never bytes in the index file; in `LibraryIndexFiles.movedFolders`, so `moveIndexFiles` moves it with the profiles, and **not** in the offline copy, where an unreachable photo shows a placeholder). Keyed by `ArtistProfileKey.key(for:)`: `PodBoxArtName.folded`, the key the iPod side uses, except that a name with no letter or digit (`@`, `!!!`) is kept under the name itself, so it still has a page and photos. Such names are never looked up and never get an iPod picture: PodBox keys them 0, and its art cache (`art_cache.c` at the pinned commit) skips a person, a People file and a folder keyed 0, so no file anywhere would show. Fetched photos are stored at most 1,600 px; the owner's are kept as given up to 32 MB / 50 MP (`ArtistPictureImage.maximumSourceBytes`/`maximumSourceArea`). Lenient decoding; a load that lost anything keeps a numbered `.bak` and then deletes no photo file at all; the `.bak` files move with the index. **Another writer of the folder is merged with, not overwritten** (two Macs sharing a library): `save` reads the file again and merges three-way against what the store last read (`ArtistProfileStore.merging(mine:base:disk:)`): a profile only the file has is kept; for one both changed, a field this store changed wins and any other is the file's (both changed one field: this save, the newer edit, wins); owner facts merge field by field; who the artist is (identity, fetched, `checkedAt`, `identityChangedByOwnerAt`) moves as one: an owner identity action on either side ("Is this them?", "None of these", "Not This Artist", a pasted id, Look Up Again's reset, each dated in `identityChangedByOwnerAt`) beats any lookup, the newer owner word winning between two, and only without one does the newer `checkedAt` win; a confirmed id the merged `rejectedMusicBrainzIDs` holds falls back to `.unknown`; lists take the file's with this store's additions and removals. **The sweep deletes only what this store dropped** (`removePhoto`, a migrated photo replaced, an identity change) and nothing in memory, in the file as it reads just then, or in a backup names; a photo file this store never knew stays. A default photo whose file has gone counts as no default when looking up (`lookUp(photoFileExists:)`) and is found again; an owner-picked one keeps its reference and shows the placeholder. Still one store per folder in the app: `currentArtistProfileStore()` makes it off the main actor and again when the folder or the location case changes; **every writer goes through `withArtistProfileStore`**, which holds the store as in use, and a new store is made only once every holder is done. **Moving the index freezes the store** (`freezeArtistProfileStore`): writers wait, the worker's unsaved results are written, and the store thaws once the new folder is in effect; the worker's apply goes through `withArtistProfileStore(ifKey:)`, so it lands nothing in a store other than the one its lookup read.
- **Owner over fetched.** A profile keeps `fetched` and `owner` `ArtistFacts` apart and `facts` shows the owner's value field by field (an owner's empty string clears a field). A lookup writes only `fetched`, `identity` and `checkedAt` (`applyFetched`), and every write of a lookup result is a compare-and-apply under the store's lock against the identity the lookup started from (`ArtistLookupResult.basedOn`): owner facts, owner photos, `defaultPickedByOwner`, `noPhoto`, `notOnIPod` and `rejectedPhotoSources` are never changed by a lookup. App paths that build a lookup result go through `ArtistLookupRun.lookUp`; owner actions (paste an id, pick a candidate) write the store directly.
- **Identity states.** `unknown`, `confirmed(musicBrainzID:wikidataID:)`, `uncertain(candidates)`, `notFound`, `rejected` ("None of these"). `ArtistIdentityMatcher` reuses the picture finder's rule against MusicBrainz release groups: exactly one confident candidate confirms; same-named acts ("Boston", "Air") and generic or self-titled albums never do, and the page asks "Is this them?". A confirmed artist is refreshed by its id (a 404 resets it to `unknown`); "Not This Artist" rejects that id for good; a new id drops what was found by the name (Deezer and Commons photos). Facts and bio come only under a confirmed identity; a Wikipedia bio always shows "From Wikipedia, CC BY-SA 4.0" and links its article, in the system's preferred language when that Wikipedia has a sitelink, else English.
- **The lookup worker** (`ArtistLookupWorker`, started a minute after launch by `startArtistLookupWorker`, and only once `migrateArtistPicturesIfNeeded` has settled: succeeded, or nothing to carry over): one artist at a time, every MusicBrainz request in the gate's **background lane**, so FIX TAGS, artwork search and DEEP SCAN never wait behind it; Wikidata, Wikipedia, Commons and image requests at the app's one Wikimedia spacer (a request a second), Deezer at most one a second. Each artist's Wikidata item is read once, for the bio and the image. **The run never asks the finder's own Commons source**: under a confirmed identity Commons is left out (the artist's P18 is known or there is none; any other Commons pick is a namesake's), and under any other the Commons candidates come from the identity search's own lookups (`LookupCommonsSource`, their Wikidata ids), never a second MusicBrainz search. That second search over namesakes ("Low", "Genesis") is what once ran past the photo's time on every try and stalled the worker on one artist for good. **A photo search that runs out of time** (30 s in the background) is no photo this time: the identity and facts land, nothing about a photo is stored, and the artist's photo is left alone for the session (`ArtistLookupResult.photoTimedOut`, `ArtistLookupSession`). A whole lookup past 180 s is `ArtistLookupError.timedOut` (`ArtistLookupRun.bounded`); three of those in a row for one artist skip it for the session. Order (`ArtistLookupScheduler.due`): the inspected artist and the one playing from the library first, once per launch, then most tracks first, from every track in the track store whichever crate is browsed (`ArtistLookupLibrary`). Due: never checked, confirmed older than 180 days, not found older than 30; never uncertain or rejected automatically; Various Artists, Unknown Artist and names that fold to nothing never (`isLookedUp`). Pauses (`ArtistLookupPauses`): the switch (Settings ▸ Integrations ▸ "Look up artist info and photos", `PreferencesStore.artistLookupsEnabled`, on by default; off cancels the lookup in progress, Look Up Again still works), `scanProgress.isRunning`, `isDeviceBusy || isConversionRunning`, `AppVisibility` hidden, Low Power Mode, `NWPathMonitor` offline, library disconnected. Failures (`ArtistLookupSession`, `ArtistLookupScheduler.failure`, `backoff`): nothing is stored; the pause doubles from 30 s to 30 minutes and resets on a success; a transport error, 5xx or rate limit retries the same artist, an answer that cannot be used skips that artist for the session, an unwritable store stops the worker until the store is made again. A newly inspected artist or a new track wakes it, but `wake()` ends only an idle or paused nap, never a failure's back-off. **Saves are debounced** (`ArtistLookupSaveSchedule`): a result lands in the store's memory at once, and the file is written at most every 30 s or every 20 results, and when the worker pauses or goes idle, before the store is swapped or the index moved, at quit and on the library drive's will-unmount. Logs carry an error's case only (`LibraryViewModel.logCase`), never its text, which can hold a path or a name. A result that lands after the library went away, the switch went off or the store was replaced is dropped silently (no `refuseWhileLibraryDisconnected` notice for work nobody asked for).
- **What the views observe.** The profiles and the running-lookup set live in `ArtistProfilesModel` (an `ObservableObject` injected beside the view model), which only the artist page, the Edit sheet, the photo viewer and the inspector's choice of page (`inspectedArtistName(knownBy:)`) observe; `reloadArtistProfiles` compares off the main actor and publishes only a real change. `ArtistLookupLibrary` is built once per index change (`artistLookupLibrary()`), never per artist. The Artist Pictures sheet holds no store: it asks for the current one on each action.
- **One lookup per artist at a time.** `artistLookupsRunning` covers the owner's lookups and the worker's; a Look Up Again, a confirmed candidate or an identity saved in the Edit sheet while one runs is queued in `artistLookupsQueued` (latest ask wins) and runs when it ends (`finishArtistLookup`), never dropped: the running one's result is refused by compare-and-apply, so a dropped refresh would leave a new id with no facts.
- **Photos.** Only the photo a lookup makes the default is downloaded (once: the finder's own download is reused); other candidates stay references (`photoCandidates`) fetched as thumbnails on demand through the one shared `artistPictureFetcher`. A photo the owner removes is remembered by source and id (`rejectedPhotoSources`) and never re-added. Until the owner picks (`defaultPickedByOwner`) the default is the best confident match: library folder image, then the confirmed artist's Wikidata image, then the finder's pick when `ArtistPhotoTrust` takes it (confirmed: a Deezer pick must fold equal to the confirmed name; not confirmed: two shared telling titles, else it is held as a candidate). No Photo survives a change of default made by a lookup; an owner's pick in the Artist Pictures sheet ends it. Removing the default makes the next photo the default and clears the owner's pick. `noPhoto` shows the placeholder and sends nothing to the iPod; `notOnIPod` sends nothing and hides nothing.
- **Migration.** `ArtistProfileMigration` carries `library.cdartists` into profiles once (`picturesMigrated` in the file): prepared bytes become `.migrated` defaults (owner-picked when `pickedByUser`), "No Picture" becomes `notOnIPod`, held candidates carry over; the worker later swaps a migrated 400 px photo for its full-size original. Run from `refreshAvailableCrates` whenever the folder resolves and the old file is there, never while disconnected.
- **When the page shows** (`ArtistPageFocus`): while the focused browser column shows Artist or Album Artist, or while "Show Artist" (a track's menu, the album page's artist link) is set until the owner clicks a row or moves columns; outside the local library only an artist the library knows. Library stats (`ArtistLibrarySummary`) are computed once per index change off the main actor, never per click. Edits (Edit Artist sheet, from the root) stage facts and identity until Save; photo actions apply at once. The Edit sheet, the viewer and the page all present from the root (`LibraryPresentations`), so the compact player shows them.
- **DEBUG hooks.** `CRATEDIGGER_ARTIST_PAGE=<name>` seeds a made-up library of three artists and their profiles into `CRATEDIGGER_CRATES_DIR` (refused unless that is outside `/Volumes` and `CFFIXED_USER_HOME` is set) and puts the inspector on `<name>`; `CRATEDIGGER_ARTIST_EDIT=1` adds the Edit sheet, `CRATEDIGGER_ARTIST_VIEWER=1` the photo viewer. The worker does not start under it, so nothing goes on the network.
- **Rules a change must not break.** Nothing the owner set is changed by a lookup. A failure is never stored, and never read as "not found". One artist the services cannot answer in time never holds the rest of the library back. A save never deletes a photo file it did not drop itself, nor overwrites another writer's profiles. Same-named acts and generic names are never confirmed automatically. Foreground MusicBrainz requests never wait behind background ones. No image decoding, store I/O or library walk on the main actor. One profile store per folder, and every writer through `withArtistProfileStore`. Every owner action that writes starts with `refuseWhileLibraryDisconnected`. The iPod's picture comes from the default photo, and the planner's safety rules and the door stay as they are. Requests carry only artist names and MusicBrainz/Wikidata ids, under the app's generic client name.

### Radio / YouTube streaming

A second playback path that streams YouTube audio instead of local files. Entirely in Core except the `LibraryViewModel+Radio` wiring.

- A **`StreamSource`** (`Models/StreamSource.swift`) is a saved YouTube URL + `StreamKind` (`live`/`video`/`mix`/`playlist`) + `StreamProvider`. Sources are grouped in the sidebar by **`RadioCategory`** (`youtubeLive` → "YT Live", `youtubeRecords` → "YT Records"), which is the payload of `LibrarySource.radio`.
- **`StreamURLParser`** normalizes a pasted URL into a `StreamSource`; **`StreamStore`** persists the list as a small JSON blob in `PreferencesStore` (app-global, *not* a per-folder `.cdcrate`).
- **`StreamResolver`** invokes **yt-dlp** to turn a `StreamSource` into a `ResolvedStream` (HLS `.m3u8` for live, progressive m4a/AAC for VOD — formats AVPlayer can decode, unlike YouTube's default WebM/Opus). The argument vector is pure and unit-tested with a fake runner. **`StreamMetadataService`** fetches title/channel/thumbnail/viewers/`StreamChapter`s.
- yt-dlp is resolved by `ExternalToolLocator` (`ToolKind.ytdlp`, binary name `yt-dlp`) with the same priority chain as ffmpeg/ffprobe. Missing yt-dlp degrades radio, not the rest of the app.

**Downloads.** A stream's audio can be saved for offline listening. **A download is a property of the stream, not a record you dug: it does not enter the library.** It lives in Radio ▸ Downloads, the stream plays from the local copy, and the Prep Crate never sees it — staging is for folders you are about to file, and a download is already where it belongs. Filing it is a separate, explicit act (`addDownloadToCrate`, the row's Add to Crate menu), and the only way it becomes a `LoadedTrack` that conversion, Record Divider and device transfer can reach — which is how a multi-chapter download gets split into per-track files for an external device.

- **`StreamDownloader`** (Core) plans the destination (`<root>/<Channel>/<Title>/<Title>.m4a`, one folder per download so its `cover.jpg` belongs to it alone), builds the yt-dlp argument vector, and parses its progress lines. It runs through **`StreamingCommandRunning`**, a second command-runner protocol that exists beside the shared `CommandRunning` for one reason: `CommandRunning` reads a process to end of file, so it can neither report progress mid-run nor be stopped, and a download needs both. Consolidating the two would break cancel and the progress bar, not simplify anything.
- **`StreamSource.downloadedPath`** plus `isDownloaded(fileExists:)` check **both** the stored path and that the file is actually there. Once filed into a crate the download is an ordinary library track, so the user can rename it, move it, or delete it; a path whose file is gone must read as "not downloaded" rather than dangle.
- **`RadioCategory.downloaded`** is a filter over the other two categories, not a third home: `of(_:)` never returns it, only `contains(_:)` does. That is what lets one downloaded YT Records stream sit in both its own row and the Downloads row with no duplicated state.
- **`pendingStreamImports`**, consumed by `applyingPendingStreamImports` from both scan-into-the-library paths (`handleImport` for a dig or Finder drop, `addURLsToCrate` for a crate drop or an `addDownloadToCrate`), carries a downloaded file's chapter markers and tag defaults across the scan that turns it into a `LoadedTrack` (the scanner itself can't know them). Queued by `addDownloadToCrate`, never by the download finishing. Entries are pruned after five minutes, so a scan that never lands (a corrupt remux, a transient I/O error) can't strand one forever.
- **`StreamResolver.resolve(_:)`** returns the local file before it ever touches yt-dlp when a stream is downloaded, so offline playback needs neither network nor yt-dlp installed; `resolveActiveEngineKind()` also forces the native engine for a downloaded stream regardless of the WebView/native preference, since only the native engine can play a local file.
- **The rule that matters most for future work:** anything that changes a track's file path must call `streamStore.repointDownload(from:to:)` beside `ListeningStore.repoint`, not only the funnels already wired for it. Treat the list of movers as examples, not a closed set, or the next one gets missed the same way these two were: `updateTrackURLInIndex` (one track), `updateTrackURLsInIndex` (a batch, which `moveLibrary` and `consolidateLibrary` both funnel through), `rewriteTrackPaths` (used by `moveAlbumFiles`, missed during this work because it had no existing `repoint` call to grep for), and the copy-on-import branch of `importTracksIntoCrate` (missed for the same reason: copy-on-import is on by default, so this is the ordinary path right after a Downloads commit). A new mover needs the same treatment even when nothing already there hints at it.
- **`removeDownload`** trashes the offline copy rather than deleting it, and only trashes its containing folder when `StreamDownloader.isDownloadFolder` says the folder is still the one the download itself created. That check compares both the folder's name and its parent's name against the sanitized title and channel, a name match rather than proof of provenance: it takes a coincidence in both path components, not just the leaf, to fool it. This matters because a repoint (retag, auto-organize, library move) can land the track in a folder the user owns; a single-track album plus the user's own `cover.jpg` would otherwise pass a contents-only "just art left" check and be trashed along with their artwork.

### Secure Mode CD ripping

An opt-in switch (Patch Bay SECURE row, `PreferencesStore.secureRipEnabled`, off by default) that rips from raw sectors instead of the `.aiff` files cddafs presents. All logic is in Core's `Services/SecureRip/`, driven by `LibraryViewModel.ripCD` / `readDiscSecurely`.

- **Raw reads** go through `RawCDDevice`: `ioctl(DKIOCCDREAD)` on `/dev/rdiskN` (from `statfs` of the mounted volume). The console user owns that node, so no root is needed. The user area plus C2 error flags (`sectorArea 0x12`) returns each sector's 2352 audio bytes followed by its 294 C2 bytes. LBA = `CompactDiscTOC` offset − 150. cddafs's `.aiff` is AIFC `sowt` (little-endian), so raw sectors match it byte for byte.
- **`SecureRipEngine`** reads every track twice with C2 and hashes each sector. Before pass 2 (for a track shorter than the drive cache) and before every retry it reads a distant flush region, so a second read really comes from the disc. A sector is accepted after two identical C2-clean reads; after 20 attempts the most frequent value is written and the sector is reported **suspicious**. Output streams to a temp WAV (`WAVFileWriter`), so memory stays bounded.
- The verified WAVs then become the sources of the ordinary rip `ConversionJob`s, so tags, folders and formats are identical to a normal rip, and the temp folder is deleted however the rip ends. **Secure Mode never falls back to an unverified read**: a device or ioctl failure stops the rip with a message telling the user to turn Secure Mode off.
- **Guards, so a bad drive or disc can never become hours of retries and imported silence:** `SecureDiscRip` probes three sectors (track 1's start, the middle, the last audio sector) plain and with C2 before reading anything, and stops if the drive can't read raw or can't report C2 (`CDSectorReadError.noC2Support`). Pass 1 aborts when a run of unreadable sectors passes 750 (10 s) or the total passes 5% of the track (`tooManyUnreadable`). EIO is ambiguous on purpose here: a scratch, a past-leadout read and a refused C2 request can all return it, which is why these thresholds exist. The retry phase has a per-track time budget (`retryBudget`, 600 s); what is left when it runs out keeps its most frequent value and is reported as suspicious.
- Not done yet: drive read-offset correction, AccurateRip/CTDB verification, rip logs.

### Record Divider (vinyl-side rip splitting)

Splits one continuous recording (e.g. a whole vinyl side captured as a single file) into multiple per-track exports. Pure logic in Core, driven by `LibraryViewModel+RecordDivider`.

- A **`RecordMarker`** (`Models/RecordMarker.swift`) is one *kept* track = `[startSeconds, endSeconds]` + title. Playback navigates between markers; conversion cuts one output file per marker; audio outside all markers is audible-but-skipped (omitted from export). Analogous to `StreamChapter` for streams.
- **`RecordDividerService`** auto-detects breaks from sustained near-silence; `RecordDetectionSensitivity` maps a 0…1 UI slider onto a noise-floor (dB) + min-silence-duration pair (conservative by default so long songs aren't split internally).
- **`RecordTrackPlanner`** turns markers into `RecordTrackPlan`s (per-track `ConversionMetadata`, source slice, suggested base name) that then flow through the normal `OutputPathPlanner` + `ConversionService` (ffmpeg cuts the slice).

### Conversion pipeline (FFmpeg)

1. UI builds a `ConversionOptionsSelection`; `LibraryViewModel+Conversion` turns it into an **ad-hoc `ConversionPreset`** and plans `ConversionJob`s.
2. **`OutputPathPlanner`** computes each destination path. Folder modes: `sourceRelative` (mirror source tree from deepest common ancestor), `flat`, `metadataTemplate` (token order: album-artist / year / album / compilation). It guarantees **collision-safe unique filenames** (` (2)`, ` (3)`…) against both existing files and already-reserved paths in the batch. **Device runs are the exception**: the planner is asked for natural names there (`naturalNames`) and the device review decides what happens to a name that is taken (see Device transfers); the device hand-off no longer shows the Skip/Overwrite or version-folder prompts, which remain for ordinary folder conversions.
3. **`ConversionService`** (Core) builds the ffmpeg argument vector (codec, bitrate/sample-rate, artwork embedding/re-encode, metadata tags) and runs jobs via `ProcessCommandRunner` (real `Process`) on an `OperationQueue` (≈ CPU count − 1 workers). `CommandRunning` is a protocol so tests inject a fake runner.
4. Preflight before running: destination writability probe + free-disk-space estimate (`validateBatchPreflight`).
5. **Cancellation is cooperative**: `cancel()` sets a flag checked *between* job dispatches; the in-flight ffmpeg process is **not** killed (documented limitation in `ConversionService`).

### FIX TAGS and DEEP SCAN (metadata matching)

Two lookup paths behind one button, both ending in the same review sheet
(`MetadataMatchSheetView`, driven by `LibraryViewModel+MetadataRepair`).

- **FIX TAGS** (the default) is text matching: `MetadataMatchService` fans out
  over `ReleaseMetadataProvider` (MusicBrainz + iTunes), `ReleaseScorer` ranks
  the candidates and turns the winner into per-track `TrackTagProposal`s.
- **DEEP SCAN** (`FingerprintMatchService`, `LibraryViewModel+DeepScan`) is
  audio matching, for when the tags are blank or wrong and text search has
  nothing to search with. `AudioFingerprintService` runs **fpcalc**,
  `AcoustIDClient` turns each fingerprint into MusicBrainz recordings, the
  album's files **vote** on which release they all appear on, and
  `MusicBrainzReleaseClient.release(id:)` fetches the winner. The score is the
  vote share, not text similarity — the point is that it never read the tags.
  Candidates are re-badged `ReleaseSource.acoustID` so the sheet says how the
  release was found.
- **Never automatic.** Fingerprinting decodes every file, so DEEP SCAN runs
  only when the user presses for it: the sheet's DEEP SCAN key, or the action
  button on the "no match" alert.
- Track pairing goes through `ReleaseScorer.proposals(from:for:recordingIDs:)`.
  The `recordingIDs` pass is DEEP SCAN's: an untagged file has no number and no
  title, so every other pass is guessing, but its fingerprint names the
  recording outright. Empty map = the old behaviour exactly.
- **AcoustID needs an *application* key**, in `AcoustIDClient.applicationKey`.
  Registered once at acoustid.org/new-application, listed afterwards under
  acoustid.org/my-applications. It is **not** the account API key from
  acoustid.org/api-key, which signs fingerprint *submissions*; the two are
  both ten mixed-case characters and are easy to confuse. Sending the account
  key returns error code 4, "invalid API key", with nothing else wrong. If the
  constant is ever left as `AcoustIDClient.placeholderKey`, DEEP SCAN refuses up
  front rather than decoding audio for a doomed request.
- **The `+` in `meta=recordings+releaseids` must stay unescaped.** AcoustID
  separates meta values with a space and a form body decodes `+` to one.
  Percent-encode it to `%2B` and the parameter is silently ignored: results come
  back carrying scores and nothing else, which reads as an unrecognised
  recording rather than a malformed request. Cost an hour once already.

### In-app updates (Sparkle)

### External tools (ffmpeg / ffprobe / fpcalc / yt-dlp / sacd_extract)

`ExternalToolLocator` resolves binaries (`ExternalTool`: `ffmpeg`, `ffprobe`, `ytdlp`, `fpcalc`, `sacdExtract`) in this priority: **bundled** (`Bundle.main` Resources) → explicit override → env var (`CRATEDIGGER_FFMPEG_PATH` / `CRATEDIGGER_FFPROBE_PATH` / `CRATEDIGGER_FPCALC_PATH`) → system PATH (`/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`, then `$PATH`). `ffprobe` powers richer metadata via `MetadataProbeService`; if it's missing the app degrades gracefully to **AVFoundation-only** metadata, and conversion surfaces a "install ffmpeg" alert. The packaged `.app` bundles **three** binaries — ffmpeg, ffprobe and fpcalc (entitlements disable library validation so they can run).

`fpcalc` is **vendored in the repo** at `Vendor/fpcalc/fpcalc` (Chromaprint
1.5.1, static, universal) and `package-app.sh` defaults to it ahead of anything
on `PATH` — a Homebrew fpcalc links against its own ffmpeg dylibs and would
fail `require_static_tool` on a signed build, or ship and not run. See
`Vendor/fpcalc/README.md` for provenance, licence and how to replace it.
`yt-dlp` and `sacd_extract` stay bring-your-own and are not bundled.

**ffmpeg never writes to a device path.** A converting device run (hand-off, SYNC) has ffmpeg write into a staging folder on the Mac; the finished file is then copied through `DeviceTransferDoor`. ffmpeg's own output creates `._` twins on FAT and sits outside the write policy and the journal. `scripts/podbox-artname-vectors.sh` is a dev tool, not a build input: it downloads PodBox's `art_name.c` at a pinned commit into a temp folder, compiles it with a stub decoder and prints the vectors `PodBoxArtNameTests` read (needs a C compiler and, unless `PODBOX_ART_NAME_C` points at a local copy, network).

### Playback

`PlaybackService` (Core) wraps an `AVQueuePlayer` (`AVPlayerEngine`) behind the `PlaybackEngineProtocol`/`PlaybackServiceProtocol` protocols (so tests use a fake engine). It's **callback-based**, not Combine: `onStateChange`/`onCurrentIndexChange`/`onTimeChange`/`onError`. `LibraryViewModel.wirePlaybackBindings()` adapts these into `@Published` state on the main actor. Queue-based with auto-advance, shuffle, repeat modes, ±8s seek, and output-device selection.

- **Gapless** is a one-item look-ahead. The engine's `AVQueuePlayer` holds the playing item plus at most one buffered behind it (`prepareNextItem(url:)`), and when the player hands over by itself the service only moves its bookkeeping — `adoptGaplessAdvance` deliberately never touches the engine, because touching it is the gap. `indexAfterCurrentEnds()` is the one answer to "what plays when this ends", read by both the look-ahead and `onItemEnded`, so the engine can never glide into a track the service does not think is playing. Only plain local files are buffered ahead: a stream keeps the reload path (radio resolves a fresh URL per play) and DSD keeps it (decoded to a temp file, or routed to the DoP engine). The engine reports `didAdvanceGaplessly` from what the player actually holds, one runloop turn after the end notification, because `currentItem` has not caught up before that. Off-switch: Advanced ▸ Gapless playback (`PreferencesStore.gaplessPlaybackEnabled`, on by default, applied live via `"CrateDiggerGaplessChanged"`).
- A gapless advance never re-enters `.playing`, so anything keyed on that transition has to be keyed on the index change too — that is why Last.fm "now playing" goes through `sendNowPlayingIfNeeded()` from both, de-duplicated by track and cleared on pause. The scrobble itself is still driven off the time-change callback (`checkScrobbleProgress`), which is unaffected.
- **The fader's makeup gain (`AudioLevelTap.setMasterGain`, for the >0 dB boost, see `VolumeCurve`) already survives every track change and gapless handover, and does not need a fix.** `AVPlayerEngine` holds one `AudioLevelTap` (and its one `AudioTapLevelStore`) for its whole lifetime; `attachLevelMetering` builds a fresh `MTAudioProcessingTap` per item but always retains that same store, so a gain set once keeps applying to whatever plays next without the fader moving again. Investigated 2026-09-19 after a report that boost above 0 dB was inaudible: measured via the tap's own RMS (never by ear), the gain applied live was within 0.03% of the expected +5 dB, and the gain measured again after reattachment (a track change) was also within 0.03% of it. Whether that ceiling reading as subtle rather than broken is the right product outcome, versus wanting a taller boost range, was left as an open call for later, not settled by this investigation. `AudioLevelTapGainTests` (Core) guards the carryover invariant with a real `AVPlayer`/`MTAudioProcessingTap`; it needs a working audio render pipeline like the pre-existing `AVPlayerEngineGaplessTests` does, so it polls with a bounded timeout and skips rather than hangs or fails outright if nothing ever plays.
- **`VolumeCurve.readout(forPosition:unit:boostAvailable:)`** (Core) renders the OLED's transient volume readout, in dB (`label(forPosition:)`) or percent (`percent(forPosition:)`, 100 at the 0 dB detent, 108 at the top of travel) per Settings ▸ Playback. `stepped(from:by:)` is what Volume Up/Down use: a step that would walk straight over the 0 dB detent stops on it instead. All three read `playbackVolume`'s `didSet` on `LibraryViewModel`, the one choke point every volume route (fader drag, menu command, keyboard shortcut, launch restore) passes through, which is also where the readout is fired and `applyVolumeToEngines()` pushes the position to the player, the audio tap and the radio engine.

### Artwork

`ArtworkService` (Core) is a **SHA-256-hash-keyed** in-memory store (`dataByHash`) + thumbnail `NSCache`. `resolveArtwork` prefers embedded art → folder image (e.g. `cover.jpg`) → remote. Tracks reference art by `artworkHash`, not by carrying image bytes. `RemoteArtworkService` fetches remotely from four sources: iTunes then Deezer for a single front cover, and — once a MusicBrainz release is picked in the artwork sheet — the Cover Art Archive (typed Front/Back/Booklet images) plus Discogs, which carries the deep scans of physical pressings. Discogs is found by a three-rung ladder in `discogsImages(for:artist:)`: the `discogs` URL relation MusicBrainz stores for the release, else its barcode, else artist+title with the result's title checked. The sheet loads the two sources in stages (archive first, Discogs appended) because the ladder can take several seconds. Discogs needs no credentials; `PreferencesStore.discogsToken` is optional and only raises the rate limit. Assets fetched outside the scan pipeline must be `ingest`ed so thumbnails resolve. Artwork Search's per-release image counts come from MusicBrainz (`coverArtSummaries`: one release-group browse per group, carrying each release's `cover-art-archive` count), not from the archive's own index, which lives on archive.org and answered 502 or timed out for most rows in 2026-10; only GET ARTWORK reads that index. Every MusicBrainz call in `RemoteArtworkService` goes through `musicBrainzData`, which waits at Core's `MusicBrainzGate.shared` (about 1 req/s; the slot is claimed before sleeping, `holdOff` after a 503, 503 retried), and a non-2xx answer throws rather than reading as "no images". **The gate is process-wide, not per feature**: artwork search, FIX TAGS and DEEP SCAN (`ReleaseMetadataProvider`), CD lookup (`CDDiscLookupService`), the artist-picture Commons source and the artist profiles' `ArtistInfoClient` all take `gate: .shared`, because MusicBrainz limits the client, not the feature. A new MusicBrainz caller takes the shared gate; one that makes its own is the way to a 503 the next time two features run together. **It has two lanes** (`wait(lane:)`): a foreground request claims the next free slot at once; a background one (the artist lookup worker) claims nothing while it waits and goes only when its slot has come and no foreground request is waiting, so a foreground request is always next out however many background ones queue. Work the app starts by itself passes `.background`; anything the owner pressed stays `.foreground` (the default). The sheet's filter/sort/group/best-match and its empty/loading/failed states are Core's `ArtworkReleaseList` and `ArtworkGridStatus`; DEBUG `CRATEDIGGER_ARTWORK_SEARCH=<title or artist>` opens it for a snapshot. Album folders can carry an `ArtworkManifest` (role mapping) and `AlbumBooklet` (scanned images/PDFs). **In-place rewrites (Edit Tags, embed and strip art) write their ffmpeg temp file beside the track as a hidden `.cratedigger-<purpose>-<UUID>.cdtmp`** with the muxer named (`MetadataEditorService.temporaryURL`, `outputMuxer`): the old `cratedigger-art-edit-<UUID>.m4a`, left empty by a quit mid-embed, was scanned as a track by CrateDigger and PodBox alike. A background cover embed reports the tracks it could not rewrite, and quit waits for it (`artworkEmbedsRunning`, `applicationShouldTerminate`).

### Cross-cutting events & persistence

- **NotificationCenter with string names** is used for several cross-cutting signals (e.g. `"CrateDiggerAudioDeviceChanged"`, `"CrateDiggerCDSpeedChanged"`, `"CrateDiggerMoveLibrary"`, `"CrateDiggerConsolidateLibrary"`, `"CrateDiggerCratesFolderChanged"`, `"CrateDiggerArtworkImported"`, `AppearanceMode.didChangeNotification`). These are untyped string contracts — grep for the literal when tracing.
- **`PreferencesStore`** (Core, `.shared`) wraps `UserDefaults` and persists: window frame, recent library folders, output destination, managed-library folder, crates-index folder, last conversion selection, OLED view, shuffle/repeat, external-device profiles, Last.fm session key, custom ffmpeg path. Folder access across launches uses **security-scoped bookmarks** (`makeBookmark`/`resolveBookmark`/`refreshBookmarkIfStale`) — always go through these helpers for user-chosen folders, never store raw paths.

### UI ("Carbon" design system)

SwiftUI under `Sources/CrateDiggerApp/UI/Carbon/`. Skeuomorphic hardware look: chassis layers, recessed wells, paper panels, an OLED display, LED meters, physical knobs/buttons. Theming flows through the `.carbonThemed(mode:)` environment with light/dark/system `AppearanceMode` (persisted, mirrored in the AppKit menu). Layout: a header, a 3-pane `MainShell` (**Sources | Browser | Inspector**, each independently collapsible with width invariants), and a footer transport. The **`OLEDView`** enum (`nowPlaying`/`conversion`/`scan`/`remoteSync`/`dub`/`devices`/`search`/`stats`) is the mode switch that drives what the main area shows (e.g. selecting `conversion` swaps the Inspector for the "Patch Bay"). `search` is summoned by ⌘F or by typing, never listed in `DisplayModeButton.cycle` or the View menu, and never persisted to `savedOLEDView` — it belongs to a query that dies with the session. **`dub`** is the getting-audio-in screen, shared by CD ripping, SACD extraction and stream downloading; it was called `cdRip`/"CD" until the download landed on it and reported a YouTube video as "CD-RIP · Disc: CDDA · 44.1 kHz". It **keeps the raw value `"cdRip"`** so a saved `savedOLEDView` still resolves — `OLEDViewCycleTests` pins that. `DubPane` branches per source: a download is its own body, not the rip's with the wrong nouns in it.

The NOW screen's right half is a 12 × 6 **LED matrix** (`OLEDMatrix`, ticked by `MeterDriver`). It hangs off the cell rail's grid (from the 4th cell's text edge, `OLEDCells.textLeading`) and stands as tall as the title's capitals. Core's `MatrixLayout` draws it as fixed-shape segments with gutters, so a wider window spaces the columns out rather than stretching the LEDs, and it is lit in two inks, cyan or Meter High, split at `MatrixCell.hotHeat`, never a blend. What it plays is a Core `MatrixAnimation` (`Services/Matrix/`: Vertical VU, Horizontal VU, Explosions, Frame), or nothing with `.off`, which removes the matrix and its driver. Settings ▸ Interface ▸ Display Animations ticks which ones are offered (`enabledMatrixAnimations`, nil = all); clicking the titlebar status LED steps through the ticked ones plus Off (`MatrixAnimationKind.next(enabled:)`), View ▸ Display Animation lists the same set (rebuilt on open), and unticking the one on screen settles onto the next (`settled(enabled:)`). The choice persists as `oledMatrixAnimation`. Vertical VU is stereo halves mirrored from the edges, but the spectrum is measured once on a mono mix, so each half is the folded 6-band spectrum scaled by its channel's level; a true per-channel spectrum would need a second FFT and new tap plumbing. Each animation sets every lit cell's heat as well as its intensity, so the view never knows which one is running; an unlit cell keeps heat 0 (so silence equals `.dark`), and the faint print of the dark grid is tinted by the animation's `restingHeat` instead. The LED is hosted in `TitlebarButtonHostingView`, which keeps its clicks from becoming window drags.

**Compact player** (2.3): the main window can fold into one rack unit — art, the display pinned to NOW, and the footer without its locate key — via Window ▸ Compact Player (⌥⇧⌘M). It is one window and one view model:
- **What decides the layout.** `LibraryViewModel.playerLayout` (Core's `PlayerLayout`, persisted; `launchLayout` forces full with no library chosen) picks what `CarbonRootView` draws.
- **How the window follows it.** `MainWindowController` keeps a frame per layout (`savedWindowFrame` / `savedCompactWindowFrame`), sized by `WindowFramePlanner.compactPlan` from `CompactDeckMetrics`, which is also what the compact arrangement lays out from.
- **Present from the root.** Sheets, model-driven `carbonPanel`s and one-shot window triggers live in `LibraryPresentations`, on the root above the layout switch. One attached to `MainShell` or the inspector silently never shows in compact, and a `carbonPanel` whose host disappears closes while leaving its model flag set, so it can never reopen.
- **Never write `oledView` for the compact display.** It pins NOW through the `\.oledScreenOverride` environment value. The app keeps switching screens underneath, and the full window shows the latest one on return.
- **Classify new menu commands.** One that acts on the browser selection, or needs the browser, goes in Core's `CompactCommandPolicy` (`.disabled` or `.expandsFirst`) and in `AppDelegate.playerCommand(for:)`.
- **Two AppKit facts it works around.**
  - The green traffic light is full screen, not zoom, so compact sets `.fullScreenNone` to make it zoom, and zoom expands.
  - A live resize ignores `NSWindow.minSize`/`maxSize` (AppKit has reset them to zero and unbounded by then), so both layouts clamp in `windowWillResize` to limits `MainWindowController` stores itself (`resizeLimits`): the full window to its 1200 × 820 floor, the compact one to its plan.
  - On macOS 27 a double-click on the titlebar strip is delivered to the SwiftUI hosting view and AppKit never zooms, so `CarbonWindow` (`UI/CarbonWindow.swift`) performs the Desktop & Dock action itself, for the real titlebar strip only (`TitlebarDoubleClick`, tested). Widening it to the header band is what once made a twice-pressed header key zoom the window.
- **One display, one transport, two arrangements.** `ConsoleStageView` (`UI/Carbon/ConsoleStage.swift`) holds a single `OLEDDisplay` and a single `FooterShell` for both layouts and places them by `ConsoleSlots` (tested); around them it mounts either the full console's surround (brand block, switcher, `MainShell`) or `CompactArtColumn`. There is no `HeaderShell` or `CompactDeckView` any more. The views read `ConsoleStage.arrangement`, not `playerLayout`: `MainWindowController` moves the arrangement (`prepareTravel` → `switchLayout` → `startTravel` → `settleStage`), so the full console is built before anything moves and unmounted only after the window has landed.
- **A fold goes out of focus and back, and the live console never shows while the window moves.** A blurred still of the console fades up over it (`ConsoleContainerViewController.raiseVeil`: the container's layer rendered at quarter scale and Gaussian-blurred once), the arrangement is swapped under it as a cut, the window travels (`CarbonMotion.foldTravel`) with the picture stretching to fit, and the picture clears on the new layout at its final size (`settleStage` → `lowerVeil`). Timings are the `veil*` tokens in `CarbonMotion`, about 0.4 s in all. This was arrived at by measurement on 8k tracks, not taste: a resizing window with the whole console visible gets 12 to 20 frames from the window server however little the app does (console following the window, held still, slid by transforms, or fading in mid-travel were all tried); under one opaque layer it travels at full rate. The hosting view is also held at the full size for the trip (`ConsoleContainerViewController.hold`), so nothing is laid out per frame. Don't show live content during the travel, don't blur the live console (a filter over the whole tree, per frame), and don't swap the arrangement while the window is moving (50 to 90 ms stalls).
- **Context menus in the browser are `lazyContextMenu`.** A plain `contextMenu` builder runs with its row's body; the browser's menus resolve a selection against the whole source, and that made one click cost about 2 s of main-thread work across the visible rows.
- **The compact deck opens centred**, on a fold and at launch (`centringCompact`); only a screen or theme re-plan keeps its place.
- **Showing it from the command line.** The DEBUG hook `CRATEDIGGER_COMPACT` (`1`, `play`, `roundtrip`) folds the window for a snapshot. `CRATEDIGGER_MINI=1` opens the mini player, and `CRATEDIGGER_COVER=<image path>` puts that picture in the compact and mini players' art even with nothing playing, so a cover screen can be captured silently.

**Busy Signals** (2.3.1): while a job runs, its OLED screen shows a line-art picture of it, and every other screen shows a 96 × 12 "source - - - destination" mini on the annunciator rail. The jobs are CD rip, secure read, convert, scan, download and transfer. The design is `docs/superpowers/specs/2026-10-15-busy-signals-design.md`; the approved sketch is in `CrateDigger_DESIGN/busy-signals/`.
- **One truth: Core's `BusyLedger`.** It holds every job's record (kind, screen, progress, labels, started/finished, seen); only completed jobs stay once they end, and cancelled or failed ones are removed at once and answers every question the views ask: which picture a screen shows, which minis the rail shows, whether a finished mark blinks, when the next redraw is due. The view model holds one `@Published var busy`. `LibraryViewModel+BusySignals` is the only file that writes it.
- **Jobs are stamped, not inferred.** Every start site calls `beginBusyJob(kind, on:)` and every finish site calls `endBusyJob(id, outcome)`. Do not derive a job from `oledView` or from a progress channel: `conversionProgress` carries rip encodes, conversions and copy transfers, and `scanProgress` carries digs, drops and device scans. The channels only feed progress into a record a start site already began. **A new job needs both stamps.** Conversion and sync have a safety net: a record still running 3 s after its channel goes idle (or after the channel has started a newer job) is ended `.failed` and logged as a missing finish site. Scan only logs, because unstamped work shares its channel.
- **Scenes are stateless.** `BusyScenes.picture` and `.mini` (Core, `Services/BusySignals/Scenes/`) turn a `BusySceneInput` (progress, labels, quantized time, finished/mark state) into a `BusyDrawing` of line primitives in a unit space (240 × 100 for a picture). `BusyCanvas` replays that one drawing for both sizes. Time is quantized to 8 fps, and `BusyCanvas` is `Equatable`, so a tick that lands in the same step redraws nothing.
- **Who ticks.** A `TimelineView` (`BusySceneTimeline`) ticks only while a picture is running or blinking. It pauses when `AppVisibility` says no window is visible, under Reduce Motion (a still key frame), and once a finished mark has stopped blinking. A finished mark blinks for 8 s after you arrive on its screen, then holds steady. A finished job counts as seen after 1.5 s on its screen, and its mini leaves the rail then.
- **Inks.** Cyan and Meter High, and `monochromeGlass` collapses both to the OLED foreground. That is also why `monochromeGlass` now clears `meterHotOverride`: Llama '97 pins it red.
- **The four jumps to NOW are gone.** A rip, download or SACD import no longer forces `oledView = .nowPlaying` when it ends, because DUB's finished frame could never be seen otherwise. A successful rip still moves to SCAN, because the import it chains switches the glass. `importSACDISO` now has the BUSY guard the other DUB jobs have.
- **Checking it.** `CRATEDIGGER_BUSY_SNAPSHOTS=1 scripts/test.sh --filter BusySignalSnapshotTests/testWriteContactSheets` writes contact sheets of every scene and mini to `.build/busy-signals/`. The rows are Carbon, Llama '97 mono, BACKLIT and Reduce Motion. Compare them by eye against the sketch after any scene change. The DEBUG hook `CRATEDIGGER_BUSY=rip,scan[:done]` fakes jobs in a running app, and `CRATEDIGGER_OLED` picks the screen.

**Motion goes through `CarbonMotion`** (`UI/Theme/CarbonMotion.swift`): `press`, `hover`, `state`, `lampOff` (a lamp decays slower than it lit), `panel`/`reveal` (surface springs), `scrollFollow`, and the AppKit window durations. Don't pick a curve inline. Anything that *moves* goes through `movement`/`layout`/`slide(from:)`/`withCarbonMovement` so Reduce Motion shortens it to a quick ease, a dissolve or a cut (`layout` for geometry-only changes such as a pane's width); colour and opacity changes keep their animation. Keep animations off the 14k-row browser lists: `MainShell` only animates a pane when the user moves one, never on `oledView`, because typing a search flips the display in the same update as the filter.

Per-part color tokens exist so a theme can retint one thing without dragging the accents along: the six `lamp*Override` screen lamps plus `lampSearch`, `selectionGlow`/`selectionSpread`, and `transportLamp` (the LED behind the silicone caps). Each falls back to the accent it historically borrowed, so an unset token is pixel-identical to what shipped; add new ones the same way, with a swatch in `ThemeTokenCatalog` and a fallback test in `DisplayLampTokenTests`.

**Four built-in themes**: Carbon, Cobalt, Llama '97 and Pocket. The first three have no shell material and no cover look on, so they render as they always did.

**Shell materials** (2.3.4): a theme gives the chassis one material, grain, moulded plastic, brushed metal, bead-blasted metal or carbon weave, each a strength in `effects` (`grain`, `shellPlastic`, `shellBrushed`, `shellBlasted`, `shellWeave`). Of the built-in themes, Carbon wears the weave (it gave up its grain for it on 2026-11-10), Llama '97 brushed metal and Pocket moulded plastic; Cobalt is bare. `ShellMaterialTests` pins that.
- **One at a time, resolved in Core.** `ShellMaterial.resolve(effects:)` returns the winner: the first non-zero of the four new keys, grain last, so a theme that inherits a grain and sets a material gets the material without zeroing grain. `CarbonTheme.shellMaterial` is that answer, computed from the clamped values. Nothing stacks.
- **The editor writes the same rule.** The five rows are an exclusive group: switching one on writes its strength and 0 to the other four in a single assignment to `draft.effects` (one undo step), via `ThemeTokenCatalog.settingExclusive`, and a row reads ON only when it is the resolved winner, not merely non-zero. Do not let a row write its own key alone.
- **Tiles made once, never redrawn.** Each material is generated once into a pair of tiles (the positive half of its signed field as white alpha, the negative half as black), so it shows on a pale and a near-black chassis alike. A modifier at 0 is the bare view. The texture rule in `CarbonTextures.swift` outranks the metals' sheen: drop the sheen before spending frames on a resize or a fold.
- **Drawn by `carbonShellMaterial`** on `ChassisLayer`, under the same `grainFree` mask as grain (display glass, silicone caps, album art, the spinning record). The mini player is its own transparent window with no `ChassisLayer`: its glass (`MiniPlayerGlass`) gets the four new materials clipped to its own shape, and never grain, which it has never had.

**Cover screen** (2.3.4): the compact player and the mini player only, never the inspector, gallery, browser, artwork viewer or widget. `CoverScreenLook` (`coverGrid`, `coverPixel`, `coverHandheld`) is a second exclusive group; the value is how dark the gaps between LCD pixels are, and `effects["coverPixelSize"]` (1.5, 2, 3 or 4 pt, not a dial: it has no off) is read raw and snapped by `CoverScreenLook.pixelSize(from:)`.
- **Whole device pixels, or it shimmers.** Core's `CoverScreenLayout.plan` picks the cell (never under 3 device pixels), the LCD pixel count and the bezel band from the well's side and the backing scale, and `pixelSnap` moves the picture's origin onto the device grid. The LCD is an `Image` at its natural size with no `.resizable()`, and never inside a `.drawingGroup()`.
- **Rendered once per track, off the main thread.** Core's `CoverScreenRenderer` (pixels in, pixels out, no AppKit) does the grid, the pixel redraw and the handheld tone; `NowPlayingCover` runs it from its `.task(id:)`, keyed by the cover and by look, strength and layout, and caches the result. Nothing renders in `body`, and nothing is animated.
- **A bezel, not a floating picture.** `CoverScreenBezel` sets the LCD into a recessed housing (inner shadow, a lip where it meets the shell) in place of `RecessedWell`. A track with no art, or a stream with no thumbnail, shows an unlit panel run through the same renderer, so its grid is real. The spinning record is never put on the screen.
- Design: `docs/superpowers/specs/2026-11-10-shell-materials-cover-screen-pocket-design.md`.

**Checking either one.** The snapshot hook (`CRATEDIGGER_SNAPSHOT_PATH`) renders the view tree and flattens blend modes to plain source-over, so grain and every material come out wrong or invisible in it. Check them with a real window capture. The snapshot is still right for the theme editor and for layout, and `CRATEDIGGER_COVER` and `CRATEDIGGER_MINI` put the screen on show.

## Conventions & gotchas

- `LibraryViewModel` is `@MainActor`; long work (scan, convert, organize, copy) runs in detached `Task`s and hops back via `await MainActor.run`/`@MainActor`.
- Heads-up: many user-facing messages are surfaced through `appAlert = .error(title:…)` **even for success/info** ("Saved", "Library Moved", "CD Ripped!"). The tone/title in those `.error(...)` calls is often informational despite the case name — don't assume an error occurred from the enum case alone.
- New testable logic belongs in `CrateDiggerCore` with an XCTest; UI glue belongs in `CrateDiggerApp`.
- `CrateDigger_DESIGN/` and `Branding/` are design references/assets, and `website/` is the static marketing landing page — none are build inputs. `dist/` and `.build/` are generated.

# Role & Philosophy
You are an expert Apple platform engineer. All code and interfaces must adhere strictly to Apple's design philosophy: Clarity, Deference, and Depth.

## Design Philosophy
- **Clarity:** Text should be legible, icons precise, and adornments should serve a functional purpose.
- **Deference:** The UI should help users understand and interact with content, but never intrude. Use translucent materials (e.g., glassmorphism, blurred backgrounds) so content breathes.
- **Depth:** Visual layers and realistic motion communicate hierarchy and state. Use standard bottom sheets, navigation stacks, and spring-based animations.

## Coding Philosophy (Swift & SwiftUI)
- **Preview-Driven Development:** Structure your views so they are inherently preview-friendly.
- **State Management:** Use `@StateObject`, `@Observable`, and `@Environment` correctly to separate data models from view rendering.
- **System-First:** Do not over-design or reinvent system controls. Use SF Symbols, SF Pro fonts, and native list groups whenever possible.
- **Accessibility & System Adaptability:** Implement Dynamic Type and semantic colors (e.g., `.background`, `.primary`) to natively support Light/Dark mode by default.

# Corporate & Engineering Philosophy

## Core Values
- **Simplicity Over Elegance:** Choose boring, readable, and maintainable code over clever, deeply abstracted, or overly engineered solutions.
- **User-Centric Pragmatism:** Technical decisions must directly serve the user experience. Do not build features or optimizations that add no value to the end user.
- **Ownership & Quality:** Write production-ready code from the start. Include proper error handling, logging, and edge-case validation without being asked.

## Development Principles
- **Leave it Better:** Follow the scout rule. When modifying existing code, refactor obvious tech debt, update outdated comments, and improve readability.
- **Don't Assume, Ask:** If a requirement or business logic rule is ambiguous, stop and ask for clarification instead of guessing and writing incorrect logic.
- **Fail Fast & Loud:** Design systems to catch errors early in the execution cycle. Write clear, actionable error messages that make debugging straightforward.
